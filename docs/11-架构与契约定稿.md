## 一、决策摘要

| 决策 | 选择 | 依据 |
|---|---|---|
| **组织原则** | **端口-适配器（Hexagonal）打底** | 核心复杂度在「驱动外部世界」；「后端冻结」⇒ 宿主天然是端口 |
| **叠加** | **`stable/` 冻结层**（来自方案 D） | 20 键 + 值形状「一旦发版不能再动」，需独立归属 |
| **`volatile` 层归属** | = **`adapters/site/*`** | 站点改版只动这里 → 回归面最小（对应 `10` 的 12 条风控约束） |
| **store 切分** | **按「共享范围」切，不按业务域** | React 官方「状态就近」原则；原实现单一 5,486 行 store 与之冲突 |
| **React 版本** | **19** | 已确认 `@xyflow/react@12.12.0` peer = `react: ">=17"` ✅ |
| **端口数量** | **只开 4 个**，不全盘端口化 | 避免 Hexagonal 的「过度设计」代价（方案 C 的唯一缺点） |
| **依赖边界工具** | **`dependency-cruiser`**（非 eslint） | 能查环、能按深度自动私有、能证明规则会咬（技能 `setup-ts-deep-modules`） |
| **规约来源** | 3 个技能 + 官方原文 | `vercel-react-best-practices`（70 条）/ `vercel-composition-patterns` / `setup-ts-deep-modules`（已装到 `~/.codebuddy/skills/`） |
| **样式方案** | **原生 CSS + CSS Modules + `tokens.css` 为 SSOT** | 用户要求「**CSS 必须标准 + SSOT**」；ReactFlow 用官方 **85 个 `--xy-*` 变量**主题化（已核实） |
| **后端是否冻结** | **不冻结 —— 成本优先**（`electron/**` 可改，按 §6.1 判据） | 用户要求「**动后端比动前端便宜就动后端**」；避免把技术债从后端搬到前端 |
| **测试框架** | **Vitest** | 审计 B6：与 Vite 同源、零配置；`core/rules` 全部纯函数可测 |
| **测试边界** | **只测纯逻辑，不测 UI**（见 §6.5 原则 7） | 用户要求「**写测试不要测 UI，避免假守卫**」；UI 用 W15 端到端冒烟验 |
| **错误处理** | **错误透传**（生产者报错，消费者只转发） | 用户要求「**错误不可被掩盖**；缺错误去生产者补」；见 §6.5 原则 6 |
| **去重** | **三振出局**（同段代码 >2 次必抽共享组件） | 用户要求「相同代码超过 2 次就要抽出共享组件」（弹窗点空白/X 关闭等）；见 §6.5 原则 8 |
| **老数据样本** | **真实样本**（已找到） | 审计 A3：`%APPDATA%\doubao-canvas\`（含 `projects-autobackup.json` + `Local Storage/leveldb`） |

### 2.1 样式方案（**重定：CSS 必须标准 + SSOT**）

> **原则修正**：**不复用原产物的 CSS**（它是**构建产物**，不是源码 —— 用它等于把"别人的编译结果"当源码地基）。
> **CSS 必须标准**，**样式有唯一真源（SSOT）**。

#### 三层结构

```
src/styles/
├── tokens.css      ★ SSOT：设计 token（全部以 CSS 变量定义）
│                     --color-* / --space-* / --radius-* / --font-* / --z-*
├── reset.css       ★ 标准化基础样式（normalize + box-sizing + 字体栈）
└── theme.css       ★ ReactFlow 主题（覆盖官方 --xy-* 变量，见下）
src/ui/**/*.module.css   组件样式（CSS Modules，作用域隔离）
```

#### 关键决策

| 决策 | 内容 | 理由 |
|---|---|---|
| **样式语言** | **原生 CSS + CSS Modules** | 标准、零运行时、Vite 原生支持 |
| **SSOT** | `tokens.css` 的 **CSS 变量是唯一真源** | 组件**禁止硬编码色值/间距**，只引用 `var(--color-primary)` |
| **ReactFlow 主题化** | ✅ **用官方 `--xy-*` CSS 变量**（已核实 **85 个**） | **这是"标准"做法**；不用 `.react-flow__*` 类名覆写 |
| **不用 Tailwind / CSS-in-JS** | — | Tailwind 会把 token 打散到 className（**破坏 SSOT**）；CSS-in-JS 引运行时开销 |
| **不搬原产物 CSS** | — | 它是编译产物，无法作为真源维护 |

#### ReactFlow 标准主题化（**已核实可行**）

```css
/* src/styles/theme.css —— 只用官方 CSS 变量，不碰 .react-flow__* 类名 */
.xy-theme {
  --xy-background-color: var(--color-canvas-bg);
  --xy-background-pattern-color: var(--color-grid);
  --xy-node-border-radius-default: var(--radius-md);
  --xy-edge-stroke-default: var(--color-edge);
  --xy-controls-button-background-color: var(--color-surface);
  /* … 共 85 个可用变量 */
}
```

```ts
import '@xyflow/react/dist/style.css';   // ① 官方样式
import '@/styles/tokens.css';            // ② SSOT
import '@/styles/theme.css';             // ③ 主题覆盖
```

> **实测依据**：`node_modules/@xyflow/react/dist/style.css` 含 **172 处 `--xy-*` 出现 / 85 个唯一变量**。
> ⚠️ 官方 CSS 仍用 `.react-flow__*` 类名（148 处）作为**选择器**，但我们**只通过 CSS 变量覆盖**，不写类名覆写规则。

#### SSOT 检查（可执行）

- eslint 自定义规则 / stylelint：**禁止** `*.module.css` 与 `ui/**` 里出现字面量色值（`#xxx` / `rgb(`）
- 只允许在 `styles/tokens.css` 出现字面量

## 三、依赖规则（**用 dependency-cruiser 强制**）

```
lib / constants          ← 谁都能用，它不依赖谁
      ↓
stable                   ← 只依赖 lib / constants
      ↓
core                     ← 依赖 stable；**不依赖** adapters / state / ui
      ↓
adapters                 ← 依赖 core/ports（实现它）+ stable
      ↓
state                    ← 依赖 core/usecases + core/ports（用注入的 adapter）
      ↓
ui                       ← 依赖 state + core/model（只读类型）
      ↓
bootstrap                ← 唯一可以 import 全部的地方
```

**三条铁律**：

1. **`core` 不得 import `adapters` / `state` / `ui`** —— 保证领域核心可纯测
2. **`ui` 不得直接调 `window.api`** —— 必须经 `state` → `usecases` → `ports`
3. **`stable` 不得 import 任何上层** —— 冻结契约不可被业务污染

> **`volatile` 在哪？** = `adapters/site/*`。站点改版只动它，`stable`/`core` **零改动** → 回归面最小。

### 3.1 约束怎么打（**审计后重判**：选择性强化，不全局套深模块）

> **依据**：技能 `setup-ts-deep-modules`（深模块 + `dependency-cruiser`）+ 审计结论 A1。

**审计发现的矛盾**：技能要求**扁平包**（"Packages are **flat**；a package may not contain another package"），而本项目的目录是**嵌套**的（`core/` 下再分 `model/ rules/ usecases/ ports/`）。若全局套用"入口点边界"，则 `adapters → core/ports`、`ui → core/model` **全部非法**，整条依赖链断掉。

**架构师判决：不全局套用，只做「选择性强化」。**

> **判断依据不是"哪个规则更好"，而是"风险在哪、约束就打在哪"。**

| 判断 | 结论 |
|---|---|
| 深模块的收益 | **局部的** —— 真正需要强隔离的只有 `adapters/site/*`（volatile）与 `adapters/host/*`（冻结契约）。`core/rules` 那 5 个纯函数之间深导入**零风险**（无状态、无副作用） |
| 全局套用的代价 | **实打实的** —— 强制扁平包 → 目录形状锁死 + 包数膨胀到 12+，**违反 §十一「防止过度设计」** |
| 项目阶段 | 单人/极小团队重写**已知形态**的应用 → 认知负担优先 |

**落地：5 条 `dependency-cruiser` 规则（全部 `error`）**

| # | 规则 | 类型 | 说明 |
|---|---|---|---|
| 1 | **层级方向** | 层间 | `ui → state → core → stable → lib/constants`；**禁止反向**、禁止跨层跳跃 |
| 2 | **`ui` 禁 import `adapters/**`** | 层间 | 必须经 `state` → `usecases` → `ports` |
| 3 | **`stable/**` 禁 import 上层** | 层间 | 冻结契约不被业务污染 |
| 4 | **`adapters/site/*` 只允许 `adapters` 内部 import** | ★ **入口点边界（选择性）** | **volatile 隔离**：外部拿不到站点选择器 |
| 5 | **无环** | 结构 | 禁止依赖环 |

> **为什么仍用 `dependency-cruiser` 而不是 eslint**：它能**查环**、能表达"层间方向"、能**证明规则真的会咬**（eslint `no-restricted-imports` 三样都做不到）。

**落地步骤**：

1. 装 `dependency-cruiser`（devDependency）
2. `.dependency-cruiser.cjs`：写上述 5 条；**分层白名单手工列**（工具不自动推导）
3. 加脚本 `lint:boundaries`，**折进已有的 typecheck 命令**（不另开）
4. **禁止 barrel files** —— 每层暴露**若干小入口点**，不要一个巨型 `index.ts` 再导出全部
5. **证明规则会咬**：故意从 `ui/` 深导入 `adapters/site/doubao/selectors.ts` → `lint:boundaries` **必须失败** → 再还原

### 3.2 依赖注入的落点（对应组合模式的 `state-context-interface`）

> 依据技能 **`vercel-composition-patterns`**。

`bootstrap/container.ts` 是**唯一**知道"用哪个 adapter 实现"的地方：

```ts
// bootstrap/container.ts —— Provider 是唯一知道 state 怎么管的地方

const site: SitePort   = createSiteRegistry();      // 按 account.type 选 adapter

const storage: StoragePort = createLocalStorage();

```

> ⚠️ **措辞修正（审计）**：`core/rules/**` 是**纯函数**，**不接收任何注入**。端口只注入到 `core/usecases`（作为依赖）与 `state`（作为编排依赖）。

## 四、端口定义（只开 4 个）

### 4.1 `HostPort` —— 宿主能力（按用途切分，不是照抄 83 个方法）

> ⚠️ **如实说明（审计 B4）**：对外是 **4 个端口**，但 `HostPort` 内部切了 **8 个子接口**（file / clipboard / project / media / account / license / api），**实际接口面 ≈ 11 个**。
> 说"只开 4 个"是指**端口的顶层数量**，不代表抽象量小 —— 别低估。

```ts
export interface HostPort {
  readonly os: 'windows' | 'macos' | 'linux';        // 用 preload 的 process.platform，不读 navigator
  file:    FilePort;      // importFiles / saveFile / loadFile / selectFolder / download*
  clipboard: ClipboardPort; // readClipboardImage / copyText / copyImage / attachImagesToWebview / pasteToWebview / onChanged
  project: ProjectPort;   // activateProjectStorage(sync) / saveSnapshot / saveBackup / logOperation / storageSize
  media:   MediaPort;     // saveImageSync(sync) / saveVideoFromUrl / resolveImageRef / imageFetchDataUrl / captureRect
  account: AccountPort;   // ensureFingerprint / ensurePlainSession / ensureLovartContainer / clearSession / setProxy
  license: LicensePort;   // getMachineCode / getLicenseStatus / activateWithCode / exportMachineCode
  api:     ApiPort;       // apiProvidersList / apiConfig* / apiJob* / apiSetup* / onApiJobEvent
}
```

**为什么切分**：`window.api` 的 83 个方法按用途分成 8 组 → 用例只依赖它需要的那一组（**接口隔离**）。`adapters/host/electron` 实现它（唯一 `window.api` 接触点），`adapters/host/mock` 提供开发期实现。

### 4.2 `SitePort` —— 站点适配（**最易变**）

```ts
export interface SitePort {
  readonly kind: 'doubao' | 'dola' | 'lovart' | 'tapnow' | 'gpt';
  scan(account: Account, opts: ScanOptions): Promise<ScanResult>;   // 抓取（降级链内部实现）
  send(account: Account, payload: SendPayload): Promise<SendResult>; // 发送
  probe(account: Account): Promise<SiteProbe>;                       // 登录态/可用性探测
}
```

> **选择器集中在本 adapter 内**（四级降级、`data-input-engine-*`、`ability_type=17`），**不外泄**。
> 站点改版 → 只改 `adapters/site/<站点>/`，`core` 不动。

### 4.3 `StoragePort` —— 持久化

```ts
export interface StoragePort {
  read<T>(key: LsKey): T | null;
  write<T>(key: LsKey, value: T): void;
  remove(key: LsKey): void;
  // 磁盘（走 HostPort.project）
}
```
> `LsKey` = `stable/contracts/keys.ts` 的**字面量联合**（20 个键）→ **拼错键名编译期就报错**。

### 4.4 `ClockPort` —— 时序（**为了可测**）

```ts
export interface ClockPort {
  now(): number;
  setTimeout(fn: () => void, ms: number): Cancel;
  setInterval(fn: () => void, ms: number): Cancel;
}
```
> 让「生成轮询 3s / 静默 9s / 持久化防抖 600ms / 撤销合并 800ms」**可单测**（用假时钟），不用等真实时间。

## 五、状态分层（React 最佳实践的落地）

> **核心原则：store 的 slices 按「共享范围」切，不按「业务域」切。**

### 5.1 四类状态与归属

| 类 | 判据 | 归属 | 本项目例子 |
|---|---|---|---|
| **① 全局共享** | 跨多个顶层子树 | `state/slices/global.ts` | `activeId`、`projects`、`accounts`、`groups`、`proxyPool`、`apiSetup`、`saveError`、`backendErrors`、`toast` |
| **② 子树共享** | 只在画布子树内 | `state/slices/canvas.ts` | `nodes`、`edges`、`library`、`past`/`future`、`snap`、`fitViewAction` |
| **③ 纯局部** | 单个/相邻组件 | **`useState`** | 面板开合、输入框内容、拖拽中态、右键菜单位置、`splitPresetPicker` |
| **④ 派生** | 能算出来 | **渲染时计算，不入 state** | `imageGenFeed` 的过滤视图、可用账号列表、占用空间、`_persisting` |

> ⚠️ **原实现的违规点**（重写要纠正）：
> - `imageGenKeyNode` / `imageGenTarget` / `imageGenParams` 拆成三个字段 → 应**合并为一个对象**（官方「Group related state」）
> - `_persisting` 存进 store → 应**派生**（官方「Avoid redundant state」）
> - `imageGenDeliveredKeys` 若可由结果推导 → 应派生

### 5.2 三类不该进 store 的东西

1. **能算的**（派生）→ 渲染时算
2. **只在子树内的** → Context 或局部 state
3. **高频变化的** → 绝不进 Context（会全树重渲）；局部 state 或 `useSyncExternalStore` 选择器

### 5.3 slice 规模约束（**审计 B5 补**）

> 原实现是**单一 5,486 行 store**。切成 3 个 slice 后，`global.ts` 仍可能巨大 —— **必须给上限，否则重蹈覆辙。**

| 规则 | 判据 |
|---|---|
| **单 slice 建议 ≤ 300 行** | 超了就**再按「共享范围」细分**（如 `global/` → `projects` / `accounts` / `settings`） |

> ⚠️ **2026-10-10 · 本节的「老数据兼容」整体作废**（用户裁定 + 真实样本实测）
>

> **实测推翻**：5 条迁移在真实样本上**全部空转**（数据已是当前形状）⇒ 它们服务的是**不存在的用户**（旧版本数据）。
> 按 7 步法 **铁律 2**（不为存量兼容）**已删**；`08` W2 / W14 同步重定义。

> **原则修正**：`electron/**` **不是绝对冻结** —— **若动后端比动前端便宜，就动后端**。
> 依据：重写的目的是"更好的实现"，不是"自我设限"。为迁就旧后端而在前端堆 workaround，是**把技术债从后端搬到前端**。

| 层 | 能否改 | 说明 |
|---|---|---|
| `electron/**` | ⚠️ **可改，但按成本判据**（见 §6.1） | 默认不动；**改动成本 < 前端绕行成本 ⇒ 改后端** |
| `window.api` 方法 / channel / 形状 | ⚠️ **可加，慎改** | 可**新增**方法/字段；**改已有签名**需评估调用面 |

| 磁盘布局 / 快照格式 / `img://` | ❌ **不能** | 同上（老用户数据在磁盘上） |
| `core/**` `state/**` `ui/**` `lib/**` `constants/**` | ✅ 可改 | 重写范围 |
| `adapters/site/**` | ✅ 可改（**且预期会频繁改**） | 站点改版就打这里 |
| `adapters/host/mock` | ✅ 可改 | 开发期用 |

### 6.1 判据：什么时候「改后端」比「前端绕行」便宜

| 判据 | 例（本项目已知） | 结论 |
|---|---|---|
| **后端改一行，前端省几十上百行** | `lovartChromeEval` 未暴露，前端 Chrome 采集通道**整条死掉** | **改后端**（暴露它）比前端绕行便宜 |
| **后端能力缺失导致前端无法实现** | `open-lovart-chrome` 有 handler 但 preload 没暴露 | **改后端**（暴露） |
| **契约本身有缺陷，前端只能 workaround** | `saveImageSync` / `activateProjectStorage` 用 `sendSync`（阻塞主进程） | 评估：改异步要动调用面；**若调用频次低则不动** |
| **站点改版** | 选择器失效 | **改前端**（`adapters/site`），与后端无关 |
| **性能问题在前端** | 画布重渲染 | **改前端** |

**改后端的约束（3 条硬性）**：
1. **不得破坏已有方法签名**（只能新增/重载）
2. **不得改变数据格式**（localStorage / 磁盘 / 协议）
3. **改动必须回写文档**（`05-配置契约层.md` 同步更新，否则文档与实现脱节）

## 六·五、职责归位（**五原则 · 审计后补**）

> **越权 = 一个模块做了不属于它的职责。** 依赖方向一旦被破坏，架构就退化成"什么都能调什么"（= 原实现的 5,486 行单 store）。

### 原则 1 · 谁拥有状态，谁负责写

| 谁 | 能写 store? | 说明 |
|---|---|---|
| `state/**` | ✅ **唯一** | store 只能被自己改 |
| `core/usecases` | ❌ **绝不能** | 依赖方向 `state → usecases` ⇒ 反向调用 = 环 |
| `adapters/**` | ❌ **绝不能** | 同上 |
| `ui/**` | ⚠️ 只经 `state` 暴露的 action | 不得 `useStore.setState()` 直改 |

**契约（★ 必须写进代码注释）**：

```ts
// core/usecases 的返回值契约 —— 唯一的交付方式
type UsecaseResult<T> =
  | { ok: true;  value: T }
  | { ok: false; reason: FailureKind; message: string };

// ✅ 正确：usecase 返回结果，由 state 层写入
const r = await generateImage(deps, input);
if (r.ok) store.attachImageResultToNode(nodeId, r.value);

// ❌ 越权：usecase 内部直接改 store
useStore.setState({ nodes: [...] });   // 禁止
```

### 原则 2 · 事件推送只能"订阅转发"，不能"写入"

主进程推送（`onApiJobEvent` / `onDolaMedia` / `onClipboardImageChanged` / `onLovartFetch*`）的归属：

```
adapters/host/electron  →  暴露 subscribeXxx(cb): () => void   （只有订阅）
        ↓
state 层  →  订阅 + 写入 store                                  （唯一写入点）
```

**adapter 只做转发，不做解释、不做存储。**

### 原则 3 · 端口只有类型，实现只在 adapters

| 层 | 内容 |
|---|---|
| `core/ports/**` | **只有类型**（interface / type），**零实现** |
| `adapters/**` | **唯一实现处** |

### 原则 4 · 纯的归 core，脏的归 adapters

`core/**` **不得**接触：`window` / `document` / `Date.now()` / `Math.random()` / `localStorage` / `setTimeout`
→ 时间与随机性一律经 `ClockPort` 注入；其余经各自端口。

### 原则 5 · 文案 / 常量 / 阈值有唯一真源（SSOT）

| 内容 | 唯一真源 | 谁不能重复定义 |
|---|---|---|
| UI 文案（含失败 label、错误横幅映射） | `constants/text.ts` | `state` / `core` / `ui` 都不得硬编码 |
| 业务常量（网格 20 / 超时 / 阈值） | `constants/` | 各处不得写魔法数 |
| 设计 token（颜色 / 间距 / 圆角） | `styles/tokens.css`（CSS 变量） | 组件不得写硬编码色值 |
| 20 个 localStorage 键 | `stable/contracts/keys.ts` | 各处不得写字符串字面量 |
| 模型表 / 风格预设 | `constants/models.ts` / `constants/styles.ts` | — |

> **越权 4 的修正**：`state/slices/ui` 原写"错误类型→文案映射" ⇒ 映射表移入 `constants/text.ts`，store **只存"当前有哪些错误"**。

### 原则 6 · 错误透传（**生产者报错，消费者只转发**）

> **铁律**：**错误只能由生产者产生，消费者只能转发。缺错误 ⇒ 去生产者那里补，不得在前端造。错误不可被掩盖。**

| 角色 | 谁 | 能做什么 |
|---|---|---|
| **生产者** | `adapters/**`、`core/rules/**` | **产生**错误（`{ok:false, reason, message}`）；`message` 必须是**原始错误原文** |
| **消费者** | `core/usecases`、`state`、`ui` | **只能转发**（可附定位信息），**不得改写 / 不得吞掉 / 不得编造** |

**四条禁止**

| # | 禁止 | 说明 |
|---|---|---|
| 1 | **禁止吞错** | `catch {}` / `catch (e) {}` 空实现 = 掩盖真相 |
| 2 | **禁止改写 message** | `message` 必须是原始错误（`e.message` / 后端返回原文）。"友好文案"属**展示层**：在 `constants/text.ts` 里按 `reason` 映射，**不覆盖原文** |
| 3 | **禁止编造 reason** | 分类表没有的错误 → 归 `unknown` **但必须保留原始 message**，并**去 `core/rules/failure.ts` 补分类**（修在源头） |
| 4 | **禁止消费者兜底造错** | usecase 不得因"怕 UI 崩"就返回自造的错误对象 |

```ts
// ❌ 消费者造错（掩盖真相）
catch (e) { return { ok: false, reason: 'unknown', message: '操作失败，请重试' }; }

// ✅ 转发（保留原文）
catch (e) {
  return { ok: false, reason: classifyFailure(e), message: e instanceof Error ? e.message : String(e) };
}
```

**与「成本优先」的联动**：`10-后端踩坑` 记着「`lovartFetchImages` 一抛错 ⇒ **整批抓取失败**」→ 这是**生产者（主进程）该修的**：应返回 `{ok:false, error}` 而非抛异常。按 §6.1 判据，**改后端**比前端逐处 `try/catch` 便宜。

**可执行检查**
- grep `catch\s*\([^)]*\)\s*\{\s*\}` ⇒ **必须 0 命中**
- `core/usecases/**` 里不得出现 `message:` **字面量**（只能来自 `e.message` 或上游 Result）
- 错误文案映射**只能**在 `constants/text.ts`

### 原则 7 · 测试边界（**只测纯逻辑，不测 UI**）

> **铁律**：**测试只覆盖纯逻辑；UI 不写组件测试。避免"假守卫"。**

| 层 | 测不测 | 内容 |
|---|---|---|
| `core/rules/**` | ✅ **必测** | 去重阈值 8/6、环检测、提示词幂等、失败分类 14 项、指纹比较 |
| `core/usecases/**` | ✅ **必测**（注入 mock adapter） | 编排、**错误透传**、状态机、重试/换号决策 |
| `stable/migrations/**` | ✅ **必测** | 数据归一（`08` W2 / W14，2026-10-10 重定义） |
| `state/**` | ⚠️ 只测 slice 的**纯 reducer** 部分 | — |
| `adapters/**` | ❌ 不测实现细节 | 它是外部世界的薄封装，测它 = 测别人 |
| `ui/**` | ❌ **不写组件测试** | **会产生假守卫** |

**为什么 UI 测试是"假守卫"**
1. 组件测试**通过 ≠ 功能正确**（测的是"渲染出了什么"，不是"用户能不能用"）
2. UI 变化频繁 ⇒ 维护成本高、**价值低**
3. 更糟：它给人**"有测试保护"的错觉**，掩盖真正的行为缺陷

**UI 怎么验** ⇒ **端到端冒烟**（`08` W15，Playwright）：测**真实用户路径**，不测组件内部。

**可执行检查**
- 测试文件只允许出现在 `core/**/tests/`、`stable/**/tests/`
- `ui/**` 下不得有 `*.test.tsx` / `*.spec.tsx`

### 原则 8 · 三振出局（Rule of Three）—— **同一段代码 >2 次必须抽出**

> **铁律**：同一段代码出现 **>2 次**（即第 3 次出现时）⇒ **必须抽出共享实现**。
> 不是"看着像就抽"（那会导致过度抽象），而是**第 3 次出现即触发**。

**抽到哪（按性质）**

| 重复内容 | 抽到 |
|---|---|
| **UI 交互模式**（弹窗遮罩点击关闭 / X 关闭 / ESC 关闭） | `ui/common/` 共享组件（**复合组件**，见 §9.4 组合模式） |
| 纯逻辑（计算 / 转换 / 校验） | `core/rules/` |
| 通用工具 | `lib/` |
| 常量 / 文案 | `constants/`（SSOT，原则 5） |
| 宿主调用模式 | `adapters/` |

**★ 本项目已识别的重复点**（来自 `03-人类版.md` / `05-画布与交互.md`）

| # | 重复模式 | 出现处（≥3） | 抽成 |
|---|---|---|---|

**与原则 5（SSOT）的分工**
- 原则 5 管**数据**的唯一真源（文案 / 常量 / token）
- 原则 8 管**代码**的唯一实现（交互模式 / 逻辑 / 组件）

**为什么必须写死"第 3 次"**：不定量的话，要么过度抽象（第 2 次就抽，抽象错方向），要么放任重复（原实现就是后者 —— 同一套弹窗逻辑散落在十几处）。

### 9.2 官方「Rules of React」9 条（逐条对照）

| # | 规则 | 落地 |
|---|---|---|
| 1 | Components must be **idempotent** | 同 props/state/context → 同输出；**渲染中不得改外部变量** |
| 2 | Side effects **outside of render** | 副作用只进事件处理或 Effect |
| 3 | **Props and state are immutable** | 不可变更新；`structuredClone` 只用于快照 |
| 4 | **Return values / args to Hooks are immutable** | 传给 Hook 的值不再改 |
| 5 | **Values immutable after passed to JSX** | 改动要放在 JSX 创建**之前** |
| 6 | **Never call component functions directly** | 组件只在 JSX 里用 |
| 7 | **Never pass hooks as regular values** | Hook 只在组件内调用 |
| 8 | **Only call Hooks at the top level** | 不在循环/条件/嵌套函数里调 |
| 9 | **Only call Hooks from React functions** | 不在普通 JS 函数里调 |

### 9.3 官方「Thinking in React」5 步（**实施顺序**）

| 步 | 内容 | 本项目落地 |
|---|---|---|
| **1** | **拆组件层次** | 先画三栏 + 画布 + 8 类节点 + 面板的层次图（`ui/` 目录设计） |
| **2** | **先做静态版**（只用 props，**不用 state**） | **M0~M2 先渲染静态画布**（假数据），再加交互 |
| **3** | **找"最小但完整"的 state 表示** | 官方**三问**：① 会变吗？② 是 props 传入吗？③ **能算出来吗？** → 能算的**不是 state** |
| **4** | **state 该放哪** | 找**最近的共同父组件**；找不到就**新建一个专门持有的组件** |
| **5** | **加反向数据流** | 父持有 state，把 `setXxx` 传下去当回调 |

> ⚠️ **Step 2 是纪律**：先静态、后交互。原实现是"边写边加交互"，导致组件巨大（`_Component42` 1500+ 行）。
