## 一、方法论坑：产出的形态

### 坑 1：手工整理产出，而不是脚本生成

**现象**：第一版 IPC 契约，我手动把 preload.js 的 83 个方法名 + main.js 的 handler 逐条抄成 markdown 表格。

**被纠正**：「不要手动，第一步就手动，后面不知道要偏移多少了。」

**根因**：把"整理"当成逆向目标。其实"整理"必须由脚本从源码推导，否则①不可复现 ②必然随数据量增大而偏移 ③无法 skill 化。

**正解**：任何产出都是 `脚本 → 读源码 → 推导 → JSON/MD`。产出文件一律脚本生成、禁止手改。

### 坑 2：把架构判断降级成手工数据文件

**现象**：想定义 BUILD-SPEC 的架构决策，我写了一个 `_spec-config.json`，手写范围/命名/模块划分。

**被纠正**：「？？？？你准备手写？」

**根因**：架构判断是"头脑 AI"的活，但它的载体必须是**脚本代码里的规则**，不是一次性手工 JSON。手写 JSON = 引入手工断点，不可复现、不可 skill 化。

**正解**：判断编码为脚本里的 `RULES` 常量（`const SCOPE_DROP=[...]`），`BUILD-SPEC = buildSpec(facts, RULES)`。改判断 = 改代码，不产手工文件。

### 坑 3：写静态清单文档，而不是可复现流水线

**现象**：想"穷尽逆向目标"，我又去写一张手写的"逆向目标全景"表格。

**被纠正**：「我要的是流水线，可复现的流水线。」

**根因**：把"规划"和"执行"混为一谈。规划文档是死的，流水线是活的 —— 后者每加一个目标 = 加一个脚本，产出可复现的 JSON。

**正解**：先有脚本清单（编号 → 目标 → 输入 → 输出 → 重跑命令），每个脚本独立可跑、幂等、锁 sha256。规划体现在脚本清单里，不体现在手写大表里。

## 二、认知坑：结论怎么下

### 坑 4：误判「渲染层到不了真源码，只能语义注入」

**现象**：我基于"渲染层 minified、shared.js 零中文"判断 store 语义要靠 action 引用图猜。

**反转**：03 脚本一跑，store 的 **61 state + 166 action 全是语义名**（`nodes/edges/past/future`、`onNodesChange/commit/undo/redo`、`addVideoNode/submitApiJob`）。名字根本没被 minify 破坏。（后经 IIFE 归类修正为 62/165，见坑 13。）

**教训**：不要用"minified 不可逆"当定论去脑补结论 —— **先让脚本跑一遍，用事实说话**。

### 坑 5：用「分级 L3 占位」把难点甩给下游 AI

**现象**：我把渲染层标成 `L3 待采`，自以为"分级"是诚实。

**被纠正**：「你把责任全推给写代码的 ai 了，他等下一看就会说，这是个大工程。」

**根因**：把"逐字翻译不可行"偷换成了"渲染层只能留白"。逐字翻译确实不可行，但**行为规格化重写**完全可行（用中文文案 + IPC 调用 + store 字段三个锚点），而且这个重活恰恰必须由"头脑 AI"扛。

**正解**：分级只允许落在"单个字段的细节不确定"，**不允许整块组件留白**。

### 坑 6：46.7MB 语义图归属误判

**现象**：我断言 `records[6]` 的 46.7MB `semantic_graph` 是"渲染层语义图"，并据此写进文档。

**反转**：实测 `records[6]` 的 `input_path` 是 `.../resources/app/electron` —— 它是**主进程**语义图（28374 节点，`module_path` 精确到 `main.js`/`api/*.js`）。渲染层是 `records[1]`（8.7MB，且 REA 对渲染层语义 **OOM 只留 380 模块清单**）。

**教训**：下结论前看 `input_path` / `module_path` 的**实际值**，别凭"大 = 渲染层"的直觉。

### 坑 7：把「函数体没提」说成「函数体不可逆」

**现象**：03-store 只输出「action 写哪些字段 / 读哪些字段 / 调哪些 IPC」，把函数体整个丢掉，然后在缺口清单里写「action 函数体 minified（`t/n/ee`），静态不可逆」。下游 AI 的判定因此是「推断量 ≈ 重写量」。

**反转**：函数体**完整可读**。`commit: n => { const r = get(); if (n && r._lastCommit && ... < 800) {...} }` —— 只有局部标识符被压成 `n/r/l`，控制流、字符串、常量、字段名全在。

**正解**：
1. **原文内联，不摘要**：每个 action 的函数体整段交给下游（165 个函数体，5398 行）。
2. **参数规范化**：store 形参 `e`/`t` 改写成 `set`/`get`（同名遮蔽时放弃改写并标注），函数体立刻可读。
3. **helper 一起给**：action 调用的顶层定义（`Mb`/`Td`/`Mr`…38 个）原文一并内联，逻辑才闭环。
4. **补事实**：`const r = get()` 的间接读取、字符串/数字常量（`800`/`80`）、UI 文案。

### 坑 8：把「脚本没解析绑定」说成「按钮是 UI 切换」

**现象**：04-components 用「按钮文案 + 后 80 行里有没有 `L.getState`/`window.api`」判断，把 280/294 个按钮判成 `UI切换`；14-flows 只认 `setter(x => !x)` 一种形态、面板要求 className 同行，294 个按钮只追出 **1** 条链路。

**反转**：组件里的 store 是**局部变量绑定**的。`const l = L(B => B.onNodesChange)`、`const le = g.useCallback(B => { L.getState().arrangeNodes(B); he(false) })` —— 建出「局部变量 → store 字段/action」映射后，按钮链路全部可追。

**正解**（1 条链路 → 246 条；按钮解析 14 → 119）：
1. **先建绑定表**：`L(x=>x.f)` 选择器 / `useState` 的 `[state,setter]` 对 / `useRef` / 局部函数（`useCallback`、箭头、`function`）。
2. **解析 handler**：内联箭头、裸变量名（追到局部函数）、`window.api` 别名（`(ee = window.api) ? ee.openExternal`）都要覆盖。
3. **以控件为单位**（见坑 28）：按钮解析结果一次给全（图标 + 文案 + title + 事件 + 来源 + 解析链）。

### 坑 9：零值不追问

**现象**：12-component-tree 报「依赖边：import 84 + **JSX 0** = 84」，JSX 边一条都没有，却没人追问为什么，直接交付。

**根因**：把「脚本没算出来」默认成「本来就提不出来」。**0 是异常信号，不是结论。**

**正解**：任何 `0` / 异常小的数都要能解释。JSX 边 = 0 的真因是三个叠在一起的作用域/词法问题（见坑 15、16、11），修完 0 → 53。

## 三、脚本技术坑

### 3.1 词法与扫描

### 坑 10：扫描器不认正则字面量 → 静默吞代码

**现象**：给脚本加「注释屏蔽」时，朴素扫描器把 `//` 一律当行注释，于是 `shared.js` 里的 `/^https?:\/\//i` 被误判 —— 从 `\/\//` 开始把该行剩余代码全挖掉，其中包括 `)) {` 的 `{`；括号配平因此提前归零，store 只扫出 **47 state / 123 action**（少 57 项）。**且不报错**：产出照写，只是内容静默变少。

**为什么危险**：这类 bug 的症状是「结果少了」，不是「脚本崩了」；只看退出码 0，就会把缺失当正确往下游交付。

**正解**：写统一词法 `readToken(text, i)`：字符串/模板串/**正则字面量**/注释整段识别，其余为 code；所有扫描器（注释屏蔽、括号配平、语句结束、顶层定义、按钮解析）都基于它。正则起始判定用「前一个有效字符 + 关键字」启发式，并排除 `++`/`--`（`a++ / b` 是除法）、排除 `<`/`>`（JSX 的 `</div>`、`<br/>` 太多）。

**验证方法**：改完立刻对账 —— 注释屏蔽后 store 应扫出 **62 state / 165 action**。对不上就是词法有问题。

### 坑 11：扫描器不跳字符串/模板串 → 假标签

**现象**：`shared.js` 里拼 HTML 的模板串被扫出 `<iframes` / `<TYPES` 之类的「JSX 标签」，混进组件树依赖。

**正解**：同坑 10 —— 标签扫描也走 `readToken`，字符串/模板串整段跳过。`jsxTags()` 只在 code 段上匹配 `<Name`。

### 坑 12：非贪婪正则停在嵌套 `{}` → 字段静默漏行

**现象**：06-数据流 的字段表漏了 `imageGenKeyTarget` / `imageGenJobNode` 两行 —— 这两张表在 04-store 的 body 里明明写着。state 覆盖率只有 58/62。

**根因**：`writesOf` 用 `set\(\s*(?:\w+\s*=>\s*)?\(?\s*\{([\s\S]{0,300}?)\}` 抓 set 的对象字面量，`[\s\S]{0,300}?` **非贪婪，停在第一个 `}`**；真实代码是

```js
set(l => { return { imageGenKeyNode: { ...(l.imageGenKeyNode || {}), [n]: r }, imageGenKeyTarget: {…} } })
```

第一个 `}` 属于 `...(l.imageGenKeyNode || {})` 的内层对象 → 捕获区在到达 `imageGenKeyTarget` 之前就截断了。另外**块体形态**（`set(l => { return {…} })`）整体被当成一个「块」，字段落在 depth 2 上，也整块漏掉。

**正解**：不用正则抓括号内容 ——
1. **括号配平**定位 `set(` 实参；
2. 在实参里找对象字面量，覆盖三种形态：直接对象 / `=> ({…})` / `=> { … return {…} }`；
3. 用**深度 1 的 key 扫描器**（`objectKeys`）取字段，正确处理简写 `{ a }`、展开 `...spread`（不是 key）、计算键 `[n]:`（不是 key）；
4. 补一层「任意深度上确实是 state 字段名」的补充，覆盖 `...(cond ? { field: … } : {})` 条件展开。

**验证方法**：`有写` 140 → 151 个 action；`writesUnknown` 归零（说明不再被嵌套对象截断）；state 覆盖率 58/62 → **62/62**。

### 坑 13：「含 `=>` 就是函数」→ IIFE 初始值被当成 action

**现象**：store 的 `activeDoubaoAccountId: (() => { … })()` 是**初始值**，却因为「值里含 `=>`」被判成 action，于是 state 61 / action 166。

**正解**：判「是不是函数值」要更严 —— `/^(?:async\s*)?(?:function\b|[A-Za-z_$][\w$]*\s*=>|\([^()]*\)\s*=>)/`，并且**括号配平后若紧跟 `(`，说明是 IIFE**（`(() => {…})()`），不算 action。修正后 62 state / 165 action，state 类型标 `computed`。

### 坑 14：各脚本各写一套括号配平

**现象**：03/04/12/14 各自写了 `balancedEnd`、注释跳过、字符串跳过、顶层定义扫描 —— 同一个 bug（不认正则）要在四处各修一遍。

**正解**：抽 `scripts/_lib.cjs` 共享库：`readToken`（词法）、`blankComments`、`balancedEnd`、`stmtEnd`、`topLevelDefs`、`objectKeys`、`jsxTags`、`importsOf`、`parseButtons`、`buildBindings`、`effectsOf`、`analyzeComponent`。**词法只有一处实现，改一次全脚本受益。**

### 3.2 作用域与解析

### 坑 15：别名表建错作用域

**现象**：12-component-tree 的 JSX 边为 0。`_cmp_X` 别名只从 `shared.js` 的 import 建，但组件文件里的标签用的是**该文件自己的** import 别名（`_Component42.jsx` 里是 `<_cmp__Component37>`，`shared.js` 里根本没这个 import）。

**正解**：别名表**按文件**建（`importsOf(text)`），再叠 `shared.js` 的作用域。

### 坑 16：包装层没穿透

**现象**：组件文件从 `./shared.js` 具名导入的 `_Component39` / `NM` / `F3` / `OM`，在 `shared.js` 里只是**一层包装**（`_Component39 = Tb(_cmp_oM)`、`NM = g.memo(_cmp_ik)`），不顺着这一跳还原到真实 `.jsx`，就永远解析不出。

**正解**：建 `wrapperTarget` 表（`shared.js` 顶层定义的 head 里含 `_cmp_X` → 还原到对应 `.jsx`），解析时**一跳穿透**。命中 38 个包装。

### 坑 17：形参遮蔽没处理

**现象**：`onClick={$ => { return $.preventDefault(); }}` —— 文件里恰好有 `const $ = be => {…}`，于是把箭头形参 `$` 当成了外层局部函数，解析出错误结果（或整条判成未解析）。

**正解**：解析 handler 前先取**本片段自身箭头函数的形参名**作为遮蔽集（`shadow`），遮蔽外层同名绑定；被遮蔽的名字按「宿主/未知值」处理，不当 store 绑定。

### 坑 18：分发函数整块展开

**现象**：`ye('image')` 里的 `ye` 是分发器：

```js
const ye = B => { if (B === 'image') { be(); return; } if (B === 'video') { ie(); return; } … $(); };
```

整块展开会把**所有分支**的 action 混进「文生图」这一条链路（`addGenImage + addGenVideo + addAccountNode + …`）。

**正解**：实参是字面量时，只在函数体里取**命中分支**（`if (p === 'lit') {…}` 配平取块；`switch/case` 同理）；没有命中分支但确实是一串 `if (p === '…')` → 取**末尾兜底路径**（`ye('text')` 走最后的 `$()` → `addText`）。

### 坑 19：「找不到」不分类，一律算缺口

**现象**：组件树里 18 个「孤儿」+ 若干「未解析标签」被当成解析失败，实际是四类不同的事实。

**正解**：逐条判性质，分类输出：
- **本文件内部定义的局部组件** → 内部，不是缺口；
- **解构 props 传入的组件**（`({ CustomComponent: _Component9 }) => … <_Component9/>`）→ 由父组件提供；
- **helper 模块**（`_cmp_Nv(s, f)` 是普通函数调用，不是组件）→ 12 个；
- **未使用导出**（只被 import/export 引用）→ 6 个。

### 坑 20：试探性解析污染统计

**现象**：为校验「组件查找表」的成员是否都能解析，我调了 `resolveTag()`；而 `resolveTag` 在失败时会把 tag 记进「未解析缺口」。于是缺口里冒出 `Infinity×2 S×2 C×1 F×1 O×1` —— 它们只是某个对象字面量里的值，不是组件标签。

**正解**：给 `resolveTag` 加 `record=false` 静默模式，**校验性调用不写统计**。统计只由真实扫描路径写入。

### 坑 21：用名字前缀/大小写猜「是不是组件」

**现象**：`shared#MA` / `shared#mb` 被当成组件进了组件树。它们其实是连接线工具函数（`MA(e, {connectionMode, …})`），**大写开头但不是组件**。

**正解**：节点判定要看**定义形态**：`class … extends Component` / head 或 body 含 `memo`|`forwardRef`|`Provider`|`createPortal` / body 含 hooks / body 含 JSX。组件查找表还要求「成员过半是组件」才认（15 张表 → 4 张真表）。

### 3.3 产出与自检

### 坑 22：分片文件名带摘要 + 覆盖写 = 陈旧文件残留

**现象**：我验证幂等的方式是「跑两遍比哈希」，两次一致 → 判定幂等。但下游 AI 实测发现 `04-store/` 下有 **10 个分片文件，索引里只列了 5 个**。分片文件名带内容摘要（`01-函数体-onNodesChange…setSoundEnabled.md`），重跑时 chunk 边界变了 → 生成新名字 → **旧文件不被覆盖也不被删除**，静静留在那里。两遍哈希一致，是因为**陈旧文件两遍都在**。

**连锁后果**：同一份真相两份（编号撞号、内容大面积重叠）；grep 出双份结果；更糟的是 md 里出现 `### activeDoubaoAccountId`（上一轮它还是 action，这一轮修正成 state 了）→「JSON 说 165，md 数出 166」（见坑 26）。

**正解**：产出前 **整目录 `rmSync` 再写**。文件名带内容摘要时，覆盖写 ≠ 幂等。

### 坑 23：幂等测试只比内容哈希

**现象**：同坑 22 —— 只比较「同一份文件列表」的内容哈希，**文件集合本身的变化被漏掉**。

**正解**：幂等验证要比 `(相对路径, sha256)` 的**集合**：跑一遍记录集合，再跑一遍比对，`added` / `removed` 都必须为空。当前基线：172 个文件（BUILD-SPEC 全量 + 5 个 facts JSON）。

### 坑 24：自检靠人肉核对，不进脚本

**现象**：分片数、索引一致性、字段覆盖度这些「结构性不变量」，我一直靠人工抽查，所以坑 22 才能潜伏到下游。

**正解**：把不变量写成脚本断言，不过就 `exitCode=1`。`99-build-spec.cjs` 现在自检 6 项：
```
✓ 04-store 分片 5 个 = ceil(165/40)
✓ 04-store 索引与磁盘分片一一对应
✓ 04-store 函数体 165 个 = action 165 个，无重复无缺失
✓ 04-store 未把 state 混入 action
✓ 05-组件 组件文件 116 个，全部含源码原文
✓ 06 字段覆盖 62/62
```

### 坑 25：同一原则只修被指出的那一处

**现象**：04-store 内联了 165 个 action 函数体，但 05-组件只给「props / hooks / store 列表 / 按钮解析链」，没有函数体。下游 AI 一句话定性：**「行为住在组件里，store 只有状态搬运」** —— 它要写的 `_Component43` 的 `sendPayload`（310 行）、`_Component44` 隐形桥，spec 里零信息，那轮它回读原文 5 次。结论：**只能当对账清单，不能当照写蓝图。**

**根因**：只修了「被指出不可逆」的那一处（store），没把同一原则推到组件。

**正解**：组件按 store 同样的做法 —— **一组件一文件**（`05-组件/组件/<名>.md`）= 规格 + 按钮解析链 + **源码原文**。116 个 `.jsx`（总 0.74MB）全量内联，最大 `_Component43.md` 104KB；`shared.js` 内部定义的组件（`shared#_Component44` 等）另出 9 个文件。

### 坑 26：md 渲染器与 JSON facts 各说一套

**现象**：`03-store.json` 说 165 个 action，但 md 分片里数出 166 个名字。

**根因**：md 是从「磁盘上的分片文件」渲染的，而磁盘上有陈旧文件（坑 22），且陈旧文件是上一轮口径（state 当 action）。**同一份事实存在两个来源**（JSON facts / md 渲染），一旦上游变了，md 不跟着变。

**正解**：① md 只从 facts 渲染，不读磁盘中间产物；② 加自检断言「md 里的 action 标题集合 == JSON 的 actions，且不含 state 名」。渲染器与 facts 必须由同一次运行的同一份数据派生。

### 3.4 工程与流程

### 坑 27：反复读源码拖延，不产出

**现象**：一度陷入反复探查 skill-pack / dist-evidence / license 等文件，迟迟不写脚本。

**被纠正**：「禁止再去看源代码了，你他妈就想着偷懒。」

**根因**：用"再看一眼确认"当拖延借口。写脚本需要看源码没错，但**看的目的是写脚本，产出必须是脚本**，不能停在看。

**正解**：一次探查（确认结构）→ 立即写脚本 → 跑通 → 看产出质量。绝不"再看一眼"两次以上。

### 坑 28：把本应一起的东西拆成多个脚本（碎片化采集）

**现象**：提取按钮 UI 时，把「按钮」（文案/title/事件）和「图标」（`Hn name`）拆成两个脚本。

**被纠正**：「你把按钮和图标分 2 个脚本，你这确定不是在捣乱。」

**根因**：按钮 = `<button><Hn name="icon"/> 文案</button>`，图标和文案是同一个控件的组成部分，拆开导致 AI 拼不起来「按钮长什么样」。这是「信息分散」的变种 —— 从"跨文件分散"变成"跨脚本分散"。

**正解**：以**控件为单位**采集，一次提全（图标 + 文案 + title + 位置 + 事件 + 解析链），不按数据类型拆脚本。

### 坑 29：试图脚本化「理解」

**现象**：把「页面骨架的 4 态语义」（加载/授权/启动/主界面）写成脚本提取，结果脚本提不准 —— 把组件内 hooks 的 `if`（keydown 判断、license 判断）全当成"状态机"，真正的 4 态只识别出 1 个。

**根因**：混淆「提取」和「理解」。脚本能提结构碎片（return 分支、布局 className），但理解不了"这 4 个 return 是 4 个页面状态"的语义归纳。

**正解**：脚本是主体，人只做脚本提不准的**少量补足**，且明确标注"人工补足，非脚本产出"。不做"脚本化理解"。

### 坑 30：跨文件事实凭印象写归属

**现象**：把 `_Component44` 隐形桥写成「发送上游」。实际：`IL()` 的唯一调用点是 `Bu`（`shared.js:40415`），`Bu` 才是全仓唯一发送入口；桥只是把组件的 `sendPayload` 注册成全局槽（`L0`），真正的发送实现在 `_Component43.jsx:2700`。

**正解**：跨文件的关键事实写成**可校验的 locator** —— 把 `pattern` 写进脚本，命中才输出，行号自动算：

```js
const SOURCE_FACTS = [
  { file: 'shared.js', pattern: 'const r = IL();', text: (line) => `发送入口唯一：Bu（shared.js:${line}）…` },
  …
];
```

**查不到就不输出** —— 文档里就不会出现凭印象写错的归属。

### 坑 31：长脚本改完不 `node --check`

**现象**：在 800 行的 `99-build-spec.cjs` 里改一处 `L.push(\`…\`)`，把结尾的反引号写成了单引号，于是**整个模板串未闭合**。`node` 的报错位置在**几十行之后**的一个无关 `L.push` 上（`SyntaxError: missing ) after argument list`），完全指不到真正的错处。

**正解**：① 长文件改完先 `node --check <file>`；② 报错位置和实际错处不符时，用「反引号奇偶性」脚本逐行扫一遍，定位模板串在哪一行开始未闭合（这次就是这么找出来的）；③ 编辑工具替换多行模板串时，改完立刻 check，不要攒到最后。

### 坑 32：`node -e` 里塞复杂正则

**现象**：为了快速验证，把带 `$`、反引号、反斜杠的正则塞进 `node -e "…"`，在 PowerShell 下被层层转义（`\\\\s` → `\\s` → 字面反斜杠），报出 `Invalid regular expression: Unterminated group` 这类**与被测代码无关**的错，浪费多轮。

**正解**：临时验证一律**写临时脚本文件**（如 `scripts/_probe.cjs`）跑完即删。不要用 `node -e` 传复杂正则/模板串。

## 四、数据源坑（REA 语义图 / provider）

### 坑 33：`semantic_graph`（符号级）与 `graph`（应用级）混淆

**现象**：08 脚本从 `semantic_graph.relations` 提"跨模块依赖"，结果 **0**。

**根因**：`semantic_graph` 是符号级（28374 个函数/变量节点，relation 是模块内的 aliases/reads/calls）；真正的模块依赖在 `graph`（JavaScriptApplicationGraph：339 节点 = ipc-handler 83 + ipc-channel 83 + javascript-module 136；578 边）。

**正解**：模块依赖、IPC handler↔channel 配对从 `graph` 提；符号级统计才从 `semantic_graph` 提。改后模块依赖 133、IPC 配对 83（与 01 的 83 通道交叉印证）。

### 坑 34：启发式正则把 mime 类型当端点

**现象**：02 脚本提取 provider 端点时，把 `application/json`（Content-Type 值）当成端点。

**正解**：路径提取后加 mime 过滤 `/^[a-z][a-z0-9.+-]*\/[a-z0-9.+-]+$/`（两段小写），一行过滤掉。

### 坑 35：event 通道的 payload 提取错位

**现象**：01 脚本里 event 通道（主进程→渲染层推送）的参数提取成了 `listener`（preload 内部变量名）。

**根因**：只解析了 preload 侧的 `ipcRenderer.on('channel', listener)`，没解析主进程侧 `webContents.send('channel', payload)` 的实参。

**正解**：event 通道的真实 payload 要从主进程 `webContents.send` / `sender('channel', payload)` 的实参提取，反向关联。

### 坑 36：正则噪音（05 的 nodeActions）

**现象**：05 提取"节点创建 action"时，把 `addPreset/addVideoShare/addBackendError`（非节点创建）也收了进来，还漏了位置参数（非对象解构）的 `addText/addGenVideo`。

**根因**：用"add 开头 + 对象解构参数"做筛选，边界不清。

**正解**：节点创建 action 应通过函数体里的 `type:'xxx'` 绑定来精确定位，而非靠名字前缀猜。

## 五、交付完整性坑（覆盖边界 + 新鲜度）

> 这一类的共同症状：**交付物「看起来」完整/最新，但缺口不在报错里，而在读者的「以为」里。**
> 前两条是下游 AI 真写代码时撞到（只有写代码才会暴露「我要的东西不在 spec 里」）；
> 后两条是下游 AI 做可复现验证时撞到（只有重跑才会暴露「spec 与 facts 不同步」）。

### 坑 37：只内联「被指出的范围」，共享模块的脚本与 helper 留在 inputs 里

**现象**：组件函数体内联后（坑 25 修完），下游 AI 又反馈：

```
grep -rn 'function uD(|const uD|function cD(|const cD =' outputs/BUILD-SPEC/   # ⇒ 0 命中
grep -rn 'shared\.js' outputs/BUILD-SPEC/00-总览.md                          # ⇒ 0 命中（总览里连 shared.js 都没提）
```

它这一刀真正需要、而 spec 里没有的：`cD` 附件指纹脚本（183 行）、`_a` 附件计数脚本（175 行）、`uD` 图序比对（36 行）、`Ap` 聚焦脚本 / `vD` 去重键 / `_0` FNV 哈希。**自 spec 可读约 90 行，必须回 inputs 的约 374 行。** 差距不在"多几行"，而在性质 —— 这些是「页面侧探测脚本」与「跨组件纯 helper」，交互细节（`_a` 的"位置近邻"几何窗口、`cD` 的四种指纹形态、`uD` 的"期望项没全命中 ⇒ 不判定"）都住在里面。

**根因**：内联只做到「被点名的那两个模块」（store、组件），从没做过一次**清单式的覆盖检查** —— 「这个 bundle 里有哪些源文件？每类定义分别落在 spec 的哪一处？」。`shared.js` 是 0.99MB / 2062 个顶层定义，既不是组件也不是 store，于是整块漏在视野外。

**正解**：
1. 新增采集脚本 `19-shared-utils.cjs`（`topLevelDefList` 取**全部**顶层定义，含重名），产出 facts；
2. 99 收敛为 `10-shared工具/` 模块：**按字节预算分 12 片**（每片 80KB 级），每节 `### <名字>（源行 N，kind，category，M 行）` + ```js 原文```，形态与 04-store 一致；
3. 另给 `99-定义索引.md`（2062 行：名字 / 类别 / 源行 / 行数 / 字节 / 分片），可 grep 定位；
4. **不筛选** —— 上一轮正是因为筛选（只收 9 个 `shared__` 组件）才漏的。

**结果**：定义 2062 个（925KB / 41281 行）全部内联；分类：页面脚本 24、纯 helper 1231、组件 65、字符串常量 58、类 2、其余 682。

**教训**：内联的范围要按「**源文件 × 定义类别**」的矩阵过一遍，不能只按「被点名的问题」推。

### 坑 38：没写覆盖边界，读者把「子集」当成「全集」

**现象**：`05-组件/组件/` 下有 125 个文件（116 组件 + 9 个 `shared__*.md`）。下游 AI 原话：「**我第一眼就是这么以为的**」—— 以为 shared.js 已被覆盖。实际那 9 个只是「组件树里出现的 shared.js 组件」，shared.js 里定义的组件/helper 远多于 9 个（它用到的 `_a/cD/uD/Ap/vD/_0` 一个都不在）。而且 `00-总览.md` 从头到尾没出现过 `shared.js` 这个词。

**根因**：**文件数会暗示覆盖度**。一个筛选出来的子集，如果不显式写明筛选口径，就会被读成全集 —— 尤其当它长得像"完整目录"时。

**正解**：
1. `00-总览.md` 顶部加「**覆盖边界**」表：源 → 内容 → 落在哪个模块，并明写「125 个组件文件 ≠ shared.js 已覆盖」；
2. 每个筛选子集旁写明口径（`shared__*.md` = 组件树里出现的 shared.js 组件）；
3. **给兜底全集**：任何被筛掉的东西都必须在另一个模块里有全集可查（`10-shared工具/` 就是 shared.js 的兜底全集），并写一句大白话：**「组件看 05，shared.js 的任何东西看 10」**。

**教训**：交付物的"完整感"是设计出来的，不是默认成立的。**有筛选，就必须同时给口径和兜底。**

### 坑 39：facts 陈旧 → spec 悄悄过期，而自检全绿

**现象**：下游 AI 收到 spec 时哈希 `95f4313f…`，跑完 pipeline 后变成 `74fc4786…`。即**磁盘上的 `outputs/*.json` 与 spec 目录不同步**。而 `99-build-spec.cjs` 只读 JSON、不刷新它，自检比的也是「JSON ↔ spec」而**不是「JSON ↔ 源」** —— 于是 spec 悄悄过期，自检依然全绿。

**根因**：收敛层（99）与采集层（01..19）之间没有**新鲜度契约**。99 默认「拿到的 JSON 就是最新的」，但 JSON 可能落后于源文件，也可能落后于它自己的上游 JSON。

**正解**（两层防护）：
1. **闸门**：99 开头重算每个 facts 记录的 `inputs[].sha256` 与磁盘比对（`outputs/*.json` 这种链式依赖也一起校验 → 传递性新鲜度）。不一致就打印「该先跑哪个脚本」并 `process.exit(1)`，**拒绝生成 spec**。宁可不出，也不出过期蓝图。
   ```
   [99-build-spec] ✗ facts 已过期，拒绝生成 spec（否则产出过期蓝图）：
     - outputs/09-数据流.json：输入已变更：outputs/04-组件规格.json
         → 先跑 node scripts/09-relations.cjs
   ```
2. **指纹**：生成 `00-事实指纹.md`，把「本 spec 由哪些 facts（sha256）+ 每个 facts 的输入 sha256」写进 spec。**收件方拿到目录后可以自己比对**，判断 spec 是否与手上的 facts 同步 —— 这才是根因的正面解法（交付物自证来源）。

**教训**：只要「A 由 B 派生」，就必须有一条 **B→A 的新鲜度契约**，而且要能被执行（闸门），不只是文档里写一句。另外：**自检的比对方向要对** —— 比「JSON↔spec」只能证明渲染没错，比「JSON↔源」才能证明数据没过期。

### 坑 40：记录 input 的 sha256 时写错对象 → 新鲜度校验永远对不上

**现象**：加完新鲜度闸门后，明明刚跑过 `04-components.cjs`，99 还是报 `04-组件规格.json：输入已变更：outputs/03-store.json`。

**根因**：04 记录 inputs 时写的是
```js
{ path: 'outputs/03-store.json', sha256: j.inputs[0].sha256 }   // ← j.inputs[0] 是 shared.js！
```
即把 **03-store.json 的 path** 配上了 **shared.js 的 sha**（`j.inputs[0]` 是 03 自己的输入）。于是校验永远失败。

**正解**：`sha256: sha256(STORE)` —— 取**该文件自身**的哈希。修完闸门立刻正常（并且当场抓出了真正的陈旧项：09 依赖的 04 刚变过）。

**教训**：**「path 和 sha 必须来自同一对象」**。跨层引用（`j.inputs[0].sha256`）很容易指错，写的时候就要问「这个 sha 到底是谁的」。校验器上线后第一时间要**用「刚跑过的正常态」验证它不误报** —— 否则你会开始怀疑校验器而不是怀疑数据。

## 六、规则清单（写进流水线，不重犯）

1. **产出即脚本**：任何结论、清单、契约都由脚本从源码推导，禁手写产物。
2. **判断进代码**：架构决策编码为脚本 `RULES`，不落手工 JSON/文档。
3. **先跑后判**：判断"能不能逆"之前，先写脚本跑一遍，用事实替代脑补。
4. **看实际值**：下结论前看 `input_path`/`module_path`/`kind` 的真实值，不凭直觉归因。
5. **不甩锅**：难点必须做实到"行为规格"级，分级只落字段细节，不落整块。
6. **脚本主体，人补足**：能脚本化的全脚本化；脚本提不准的语义由人手工补并明确标注，不做"脚本化理解"。
7. **一次探查 → 一次产出**：看源码只为写脚本，不停留在看。
8. **先给原文，再给摘要**：能内联的原文一律内联，摘要只是索引。摘要代替原文 = 把推断量转嫁给下游。
9. **同一原则要一次推到底**：store 内联了函数体，组件就必须也内联（「行为住在组件里」）。别只修被指出的那一处。
10. **命名 minified ≠ 语义 minified**：压缩删的是标识符名，删不掉控制流/字符串/字段名/调用图。判断「不可逆」前先看函数体。
11. **零值要追问，不要接受**：「某类边 = 0」「未解析 = N」必须能解释。0 通常是作用域/包装层没穿透，不是「本来就没有」。
12. **词法只有一处实现**：字符串/模板串/**正则字面量**/注释统一走 `readToken`；任何自定义扫描器都要认正则，否则 `/\/\//` 会静默吞代码（症状是「结果少了」而非报错）。
13. **不用正则抓括号内容**：`set({…})`、`if (…)`、JSX 标签一律用括号配平 + 深度扫描；非贪婪 `{0,N}?` 会停在嵌套 `{}` 上静默漏数据。
14. **判函数值要严**：别用「含 `=>`」判函数 —— 括号配平后紧跟 `(` 的是 IIFE，是初始值不是 action。
15. **绑定解析是渲染层的主力**：局部变量 → store 的映射表（选择器 / useState 对 / ref / 局部函数），是把「组件行为」接回「数据流」的唯一桥。
16. **作用域要按文件建**：别名表、import 表、props 表都按文件建，再叠共享模块；包装层（`X = memo(_cmp_Y)`）要一跳穿透。
17. **形参遮蔽优先于外层绑定**：`onClick={$ => $.foo()}` 里的 `$` 是形参，不是外层同名变量。
18. **分发函数按实参裁剪**：字面量实参只取命中分支，无命中取末尾兜底；整块展开会把所有分支混进一条链路。
19. **「找不到」要分类**：分成「内部定义」「props 传入」「helper 模块」「未使用导出」，每类写清性质 —— 缺口清单才可信。
20. **试探性解析不写统计**：校验用的解析调用要走静默模式，统计只由真实扫描路径写入。
21. **判「是不是组件」看定义形态**：`extends Component` / `memo|forwardRef|Provider|createPortal` / hooks / JSX —— 不看名字大小写。
22. **产出前先清目录**：文件名带内容摘要时，覆盖写 ≠ 幂等；必须先 `rmSync` 再生成。
23. **幂等要比「文件集合 + 内容」**：只比内容哈希会漏掉文件集合的变化。
24. **自检进脚本**：结构性不变量（分片数/索引一致/无重复/覆盖度）写成断言，不过就 `exitCode=1`；md 与 JSON facts 必须同源派生。
25. **以控件为单位采集**：图标 + 文案 + title + 事件 + 解析链一次给全，不按数据类型拆脚本。
26. **交叉验证**：独立来源（源码正则 vs REA 语义图）对上才可信，如 01 的 83 = 08 的 83。
27. **跨文件事实写成可校验 locator**：`pattern` 命中才输出、行号自动算，避免凭印象写归属。
28. **长脚本改完先 `node --check`**：报错位置常与真实错处相差几十行；模板串未闭合用反引号奇偶性扫描定位。
29. **临时验证写临时脚本文件**：不要用 `node -e` 传复杂正则/模板串（shell 转义地狱），跑完即删。
30. **覆盖按「源文件 × 定义类别」过一遍**：内联范围不能只跟着「被点名的问题」走；先把「有哪些源文件、每类定义在哪」列全，再定范围。
31. **有筛选就必须给口径 + 兜底**：文件数会被读成覆盖度。筛选子集旁写明口径，全集另开模块，并给一句「什么看哪个」的大白话导航。
32. **采集与收敛分开**：采集脚本只负责「取全」（facts + 原文），分片/布局/索引交给收敛层（99）—— 这样「换一种分片方式」不用重跑解析。
33. **派生关系要有可执行的新鲜度契约**：「A 由 B 派生」就必须能校验 B→A 是否最新（重算 sha256 + 闸门拒绝生成），不能只在文档里写一句。
34. **自检的比对方向要对**：比「中间产物 ↔ 最终产物」只证明渲染没错；比「中间产物 ↔ 源」才能证明数据没过期。
35. **交付物要自证来源**：把来源指纹（facts 的 sha256）写进交付物，收件方能自己判断同步性 —— 这是「spec 悄悄过期」的正面解法。
36. **path 与 sha 必须来自同一对象**：跨层引用（`j.inputs[0].sha256`）极易指错，写的时候问一句「这个 sha 到底是谁的」。
37. **校验器上线先用「正常态」验证不误报**：否则你会开始怀疑校验器，而不是怀疑数据。
