## 执行策略（先读这里 · 让逆向更顺）

> 6 条效率杠杆，按杠杆从高到低；决定第一层怎么执行。

1. **集中火力 6 个文件，别平均用力**：业务逻辑基本压在 `_Component43`（3304 行 / 271 中文）、`_Component42`（88 中文）、`_Component45`（1427 行 / 68 中文）、`G3`（1088 行 / 44 中文）、`Z3_1`（1232 行）和 store `L`（5486 行）。其余约 110 个「工具」组件批量粗标即可。
2. **先做「中文文案 → 组件」索引**：一条 grep 生成 `文案 → 文件` 表，瞬间锚定组件职责，作为方案 1 副产品。⚠ `shared.js` 零中文，store 语义不能靠文案推，走第 5 条。
3. **60MB bundle 先切分建索引，别反复全读**：`rea-evidence-bundle.json` 的 `records[6]`（48MB）是**主进程**语义图（28374 节点 / 26865 关系），`records[1]`（8.7MB）是**渲染层**模块清单（380 节点 / 0 关系，REA 语义 OOM 放弃）。方案 1 脚本第一步按 record / 顶层 key 切块 + 建索引，后续按需精读单块。
4. **用运行时反推，别纯读源码**：重建版已能跑，方案 4 用 React DevTools 产出「组件树快照」，点元素高亮到组件，动态标注补静态分析。
5. **store 拆解用「action 引用图」做锚点**：先列全 store `L` 的 action/state 清单，再 grep「谁调用哪个 action」，让组件挂到数据流上。
6. **主链路闭环优先，别追求 7 域全覆盖**：方案 6 先只打通「画布 + 生成链路」（UI 点击 → store action → IPC 通道 → 主进程 handler → provider），其余 6 域作为变体后续补。

## ROI 路线（已验证 · 实测 rea-evidence-bundle.json + 主进程源码）

> 结论一句话：**主进程是「源码 + 完整语义图」双齐全的金矿；渲染层到不了「逐字源码」，但行为规格可提全 —— 函数体原文、按钮事件链都能拿到，不需要推断。**

> ⚠ 修订（见 `踩坑记录.md` 坑 7/8）：「渲染层只能做语义标注」是**脚本能力不足**导致的伪结论。实测 store 的 165 个 action 函数体语义完整可读（只有局部标识符被压成 `n/r/l`），组件按钮链路也能通过「局部变量绑定解析」追到 store action。真正不可逆的只剩**标识符名字本身**。

### 实测事实
- `rea-evidence-bundle.json` 两大块：`records[6]`（48MB）= **主进程**（`electron/`）语义图，28374 节点 / 26865 关系，`module_path` 精确到真实文件（`main.js`=10488、`dola-media.js`=4659、`license.js`=1953…）；`records[1]`（8.7MB）= **渲染层**（`app/`）仅 380 模块节点 / 0 关系（REA 对渲染层语义 OOM 放弃，只留 inventory）。
- 主进程 28 文件未混淆，`preload.js` 83 个 api 方法名、`main.js` 66+ 个 `ipcMain.handle` 通道名全部可读、带行号。
- `api/providers/` 下 5 个生成服务 provider（`kling.js` / `vidu.js` / `volcengine-ark.js` / `llm-openai-compat.js` / `geeknow-relay.js`）未混淆，直接揭示生成对接层。

### ROI 排序（高 → 低）
1. **主进程领域模型 + IPC 契约**（近乎零成本）：读未混淆源码 + 消费 `records[6]` 现成语义图 → 领域模型 / 66+ 通道契约 / 5 provider 规格。
2. **生成 pipeline 逆向**（高价值）：`api/providers/` 5 文件直接给出 prompt 构造、请求格式、模型参数。
3. **渲染层语义注入**（中 ROI）：REA 已 OOM，只能靠 `expanded_components`（116 组件）+ 中文文案 + 可读契约给乱码贴标签。
4. **逐字复刻 / 全量语义命名**（低 ROI，已降级）：minified 不可逆，连 REA 都做不到，不投入。

### 「流水线变源码」的现实边界
主进程已是源码 + 现成语义图（理想态已达成一半）；渲染层到不了「逐字源码」（**标识符名**被 minify 删除），但**行为**没有丢：store 166 个 action 的函数体原文、39 个 helper 原文、297 个按钮里 292 个的事件解析链都能脚本提全。ROI 最高路线：**主进程照写 → 生成 pipeline 照写 → 渲染层按「函数体 + 事件链」照写，只把标识符改名**。

（B 语义化源码降级为可选，不阻塞 C；C 直接用原 project 渲染层）
```

## 推荐执行顺序

> 按 ROI 路线，主进程线（高 ROI、近零成本）先行，渲染层线并行跟进。

1. **主进程线（先做，ROI 最高）**：方案 5（IPC 契约，只依赖 preload/main + `records[6]` 语义图）→ 生成 pipeline（`api/providers/` 5 文件）→ 方案 E 规格。
2. **渲染层线（并行跟进）**：方案 1（一键地图）→ 2（组件语义）→ 3（store 拆解）→ 6（分域收口）。
3. 重写线：C（完整复刻，用原 project 渲染层），或 D→E（干净工程 + 规格）；B（语义化源码）可选、不阻塞。
4. F（运行时录制）穿插验证。

### 重跑顺序（改任何脚本后照这个跑）

```

⚠ **99 会拒绝在 facts 过期时生成**：它重算每个 facts 记录的 `inputs[].sha256` 与磁盘比对，
不一致就打印「该先跑哪个脚本」并 `exit 1`。所以「改了源/改了前置脚本，直接跑 99」会失败 —— 这是有意的，
防止产出**悄悄过期**的 spec（详见 `踩坑记录.md` 坑 39）。
