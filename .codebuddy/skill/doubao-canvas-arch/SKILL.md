# 架构定稿：从约束推导架构

## 用途

本技能提供架构师真正需要的两样东西，外加可落地的模板与实例：

| 部分 | 是什么 | 给谁用 |
|---|---|---|
| **第一部分 · 完整推理链** | 每个结论**怎么一步步推出来的**（链不能断） | 要理解"为什么"、要迁移方法的人 |
| **第二部分 · 判据库** ★ | 给定情况 → **该做什么决策**的规则（15 类：定位/边界/抽象/数据流/质量/工具/并发/失败/状态机/安全/可观测/生命周期/性能/许可防篡改/数据模型） | 定架构、写代码、评审代码的人 |
| **第三部分 · 通用方法** | 怎么采集约束、怎么排里程碑 | 开新项目、做架构决策时 |
| **第四部分 · 本项目实例** | **指向真源 `docs/11`**（本技能只讲"怎么推"，不复制"推到哪"） | 落地/评审豆包画布代码 |
| **第五部分 · 求最优架构** | 穷尽手段找最优（外部最佳实践 / GitHub 同类 / 标准 / 反向验证…） | 想让架构逼近最优时 |
| **第六部分 · 自进化** | 把求到的"最优"留住（记账，非目的） | 每次决策/评审/改版后 |
| `references/08-默认架构模板.md` | 定死的默认（目录/接口/配置/骨架） | 直接照建，不留发挥空间 |
| `references/09-求最优与补缺.md` / `10-进化日志.md` | 同类项目登记 + 对照表 / 演进轨迹 | 求最优与进化时 |

> **为什么要"推理链 + 判据"两样**：结论换项目就变，照搬结论 = 抄错答案；**判据**是可迁移的决策规则，**推理链**是可迁移的推导范式。看懂这两样，换项目能自己推出结论。

## 元原则

**架构不是"选最先进的方案"，而是"把约束翻译成结构"。判断依据不是"哪个规则更好"，而是"风险在哪、约束就打在哪"。**

**没有落点的约束 = 实现时必然重踩。**

# 第一部分 · 完整推理链

> 架构师要的不是结论，是"结论怎么来的"。**每条链必须闭合**（事实 → 约束 → 判据 → 决策 → 落地 → 验证），任何一环缺失 = 实现时重踩。
> 下面 20 条链是本项目的全部推导。**链的"形状"可迁移；链里的"事实"不可迁移。**

### 链 1 · 为什么用端口-适配器（Hexagonal）
1. **事实**：宿主 `window.api` 暴露 83 个方法；要驱动 5 个外部站点；有 webview、磁盘交互（`00`/`06`）。
2. **约束**：核心复杂度在**驱动外部世界**，领域规则本身不复杂。
3. **判据**：A1（认识外部世界 → 适配器）+ B1（变更频率高/需强隔离 → 开端口）。
4. **决策**：外部世界变**端口**，内核保持纯净。
5. **落地**：`core/ports/`（只有类型）+ `adapters/`（唯一实现）。
6. **验证**：`core/**` 无 `window`；端口文件只有 `interface`。

### 链 2 · 为什么只开 4 个端口
1. **事实**：Hexagonal 全盘端口化会让目录膨胀、包数升到 12+。
2. **约束**：收益是**局部的**（只有站点/宿主真需强隔离），代价是**全局的**（认知负担）。
3. **判据**：B1（开端口需"是外部边界 + 高变更/强隔离"）+ B4（约束只打在有风险处）。
4. **决策**：**只对真正需要隔离的边界开端口** → 4 个（Host/Site/Storage/Clock）。
5. **落地**：`core/ports/` 仅 4 个文件；其余直接依赖 `core`。
6. **验证**：端口数量 ≤ 4；新增端口需过 B1。

### 链 3 · 为什么分 volatile / frozen 三层
1. **事实**：站点改版频繁（选择器一改就失效）；契约一旦发版不能再动（20 键 + 磁盘格式）。
2. **约束**：**变更频率不均匀** —— 最易变与最不变共存。
3. **判据**：B4（把约束打在"变化最大处"，让回归面最小）。
4. **决策**：最易变 → `adapters/site/*`（volatile）；最不变 → `stable/`（frozen）；中间夹 `core`。
5. **落地**：三层物理隔离 + 依赖方向单向。
6. **验证**：站点改版只动 `adapters/site`；`stable/` 无上层 import。

### 链 4 · 为什么 `stable/` 必须独立成层
1. **事实**：20 个 localStorage 键 + 磁盘快照 + `img://` 协议"一旦发版不能再动"。
2. **约束**：这些契约**混在业务代码里会被"顺手改掉"**。
3. **判据**：B2（冻结层独立归属）+ A1（发版冻结的契约 → 冻结层）。
4. **决策**：独立 `stable/` 层，**永不 import 上层**。
5. **落地**：`stable/contracts/keys.ts`（字面量联合）+ `schemas.ts` + `protocols/` + `migrations/`。
6. **验证**：dependency-cruiser 规则 `stable-no-upward`（`stable` 禁 import 上层）。

### 链 5 · 为什么不按业务域切 store
1. **事实**：逆向桶分类有 26.4% 误分（`09` C1）；5,486 行 store 是**跨切面**对象，按域切无处安放（`02` §6.2）。
2. **约束**：业务域边界是"**拟合**"出来的，不是源码里真实存在的边界。
3. **判据**：B4（不能用不可靠的分类当架构依据）+ A2（状态按**共享范围**切）。
4. **决策**：**按「共享范围」切**，不按业务域。
5. **落地**：`state/slices/{global,canvas,ui}.ts`。
6. **验证**：每个 slice 对应一个共享范围，而非一个业务域。

### 链 6 · 为什么 slice 要有规模上限
1. **事实**：原实现是**单一 5,486 行 store**；切成 3 片后 `global` 仍可能巨大。
2. **约束**：不给上限就会**重蹈覆辙**。
3. **判据**：C2（超阈值 → 再按共享范围细分）。
4. **决策**：单 slice ≤ 300 行 / ≤ 25 字段 / **action 只编排**。
5. **落地**：**人工 review 把关**（eslint `max-lines` 已于 2026-10-11 **关闭** —— 行数是代理指标，对纯数据/文案表与逻辑文件用同一把尺会逼出"为拆而拆"）。
6. **验证**：`global.ts` 超 300 行即拆。

### 链 7 · 为什么后端不冻结（成本优先）
1. **事实**：`electron/**` 可改；存在"前端绕行成本 > 改后端成本"的场景（如能力未暴露）。
2. **约束**：为迁就旧后端在前端堆 workaround = **把技术债从后端搬到前端**。
3. **判据**：B2（成本判据：改一行省几十行 → 改）。
4. **决策**：**不绝对冻结**，划契约边界表 + 改动判据。
5. **落地**：§判据 B2 + 3 条硬约束（不改签名/不改格式/回写文档）。
6. **验证**：每次改后端都过 B2 判据并回写文档。

### 链 8 · 为什么用 dependency-cruiser 而非 eslint
1. **事实**：需要"查环 + 表达层间方向 + 证明规则会咬"。
2. **约束**：eslint `no-restricted-imports` **三样都做不到**。
3. **判据**：F1（选能证明会咬的工具）。
4. **决策**：用 `dependency-cruiser`。
5. **落地**：`.dependency-cruiser.cjs`（多条规则，含 `core-no-react`）+ `lint:boundaries` 折进 `npm run check`。
6. **验证**：故意深导入 → 命令**必须失败**。

### 链 9 · 为什么错误必须透传
1. **事实**：原实现有"友好文案覆盖原始错误"的做法；`lovartFetchImages` 一抛错整批失败。
2. **约束**：**错误被掩盖 = 找不到根因**；缺错误应去生产者补。
3. **判据**：A4（生产者报错，消费者只转发）。
4. **决策**：错误透传 + 四条禁止。
5. **落地**：`Result` 类型 + `constants/text.ts` 做展示映射 + grep 检查。
6. **验证**：`catch {}` 0 命中；用例层无 `message:` 字面量。

### 链 10 · 为什么只测纯逻辑不测 UI
1. **事实**：原实现 UI 组件巨大（`_Component42` 1500+ 行），组件测试通过 ≠ 功能正确。
2. **约束**：UI 变化频繁 → 组件测试**维护成本高、价值低**，且给"有测试保护"的错觉。
3. **判据**：E1（测能测准的层：纯逻辑）。
4. **决策**：只测内核规则 / 用例 / 迁移；**UI 不写组件测试**。
5. **落地**：测试文件只在 `core/**/tests/`、`stable/**/tests/`；UI 用 Playwright 冒烟。
6. **验证**：`ui/**` 无 `*.test.tsx`。

### 链 11 · 为什么三振出局（第 3 次必抽）
1. **事实**：同一套弹窗逻辑（遮罩/X/ESC 关闭）散落在十几处。
2. **约束**：不定量的话，要么过度抽象（第 2 次就抽，抽错方向），要么放任重复。
3. **判据**：C1（同一段代码 >2 次即触发）。
4. **决策**：第 3 次出现**必须**抽共享实现。
5. **落地**：`ui/common/`（Modal/ContextMenu/ToastHost/ErrorBanner/EmptyState）+ `'Escape'` 只允许出现在此。
6. **验证**：`'Escape'` / `role="dialog"` 只出现在 `ui/common/`。

### 链 12 · 为什么样式要 SSOT + 原生 CSS
1. **事实**：原产物 CSS 是**构建产物**（编译结果），不是源码；ReactFlow 提供 85 个 `--xy-*` 变量。
2. **约束**：用编译产物当源码地基 = 无法维护；token 打散进 className = 破坏 SSOT。
3. **判据**：F2（标准 + 唯一真源）。
4. **决策**：原生 CSS + CSS Modules + `tokens.css` 为 SSOT；第三方库只用其官方变量主题化。
5. **落地**：`styles/{tokens,reset,theme}.css`；组件只引 `var(--*)`。
6. **验证**：lint 禁止 `ui/**` 出现字面量色值。

### 链 13 · 为什么并发要有占用与超时
1. **事实**：多任务共享账号 / 抓取通道。
2. **约束**：无保护 → 同账号并发发送 / 重复抓取 → 风控与脏数据。
3. **判据**：G1（有竞争必须有保护）。
4. **决策**：忙集合 + 负载计数 + 占用超时（1h）+ 全忙排队。
5. **落地**：`core/usecases` 池调度 + `core/rules` 决策。
6. **验证**：W11 账号池调度用例。

### 链 14 · 为什么失败要"分类"与"决策"分离
1. **事实**：失败有 14 类，不同类要不同动作。
2. **约束**：分类（是什么）与决策（做什么）耦合 → 无法单独测试与扩展。
3. **判据**：H1（分类）+ H2（决策）。
4. **决策**：分类函数（正则表）与决策函数（三选一）分离。
5. **落地**：`core/rules/failure.ts`（纯函数）。
6. **验证**：W9 表驱动单测。

### 链 15 · 为什么安全确认要停手
1. **事实**：出现"安全确认 / 人机验证"时若继续重试 → 封号。
2. **约束**：重试代价（封号）远大于收益。
3. **判据**：H3（安全优先）。
4. **决策**：命中即 `retryable:false`，停手交人工。
5. **落地**：分类表 `safety-promise`/`human-verification`/`risk-refuse`。
6. **验证**：W9 断言 `retryable:false`。

### 链 16 · 为什么状态用判别联合不用库
1. **事实**：账号 / API 任务 / 抓取都有状态流转。
2. **约束**：状态机库引入依赖与认知负担；项目形态已知。
3. **判据**：I1（够用就不引库）+ B5（拒绝过度设计）。
4. **决策**：判别联合 + 纯函数。
5. **落地**：`core/model`（判别联合）+ `core/rules`（转移）。
6. **验证**：终态穷举 + 转移单测。

### 链 17 · 为什么必须"零注入"
1. **事实**：`10` 实测 —— JS 改 UA/指纹 → 被站点判定伪造（Cloudflare 403）。
2. **约束**：引擎指纹 JS 改不了；改反而留可探测痕迹。
3. **判据**：J4（不改 `navigator`/`screen`/`webgl`）。
4. **决策**：零注入；声明版本不高于真实引擎。
5. **落地**：`adapters/site/*` 行为约定（禁注入）。
6. **验证**：站点适配器无注入代码。

### 链 18 · 为什么图片必须外置、视频必须落盘
1. **事实**：base64 全塞 JSON 是存储配额超限根因；远端直链是签名临时地址，重启后失效。
2. **约束**：大资产内联/直链 → 配额超限 + 数据丢失。
3. **判据**：L2（绝不内联 base64；视频落盘）。
4. **决策**：`img://` 外置（内容哈希，幂等）；视频落盘 `vid://`。
5. **落地**：`adapters/host`（media）+ `stable/protocols`。
6. **验证**：W3 外置幂等（磁盘侧）+ W2「读当前形状不丢」。

### 链 19 · 为什么许可要 fail-close 与防回拨
1. **事实**：纯离线客户端；系统时间可被回拨。
2. **约束**：回拨可让过期授权复活；解密失败若放行 = 授权形同虚设。
3. **判据**：N3（防回拨）+ N4（fail-close）。
4. **决策**：可信时间源 + 单调时钟 + 落盘基线；解密失败**拒绝激活**。
5. **落地**：许可模块（客户端**只含公钥**）。
6. **验证**：回拨检测；失败路径拒绝。

### 链 20 · 为什么数据模型用判别联合 + ID 前缀
1. **事实**：8 类节点；实体间用 id 引用。
2. **约束**：多态实体无判别式 → 类型不安全；裸随机 ID → 无法按类型解析。
3. **判据**：O1（判别联合）+ O2（前缀 ID）。
4. **决策**：判别联合（`type` 判别）+ 固定前缀 ID。
5. **落地**：`core/model`（判别联合 + defaults）+ ID 生成器。
6. **验证**：W13 节点类型完整性。

# 第二部分 · 判据库（★ 架构师核心工具）

> **判据 = "给定情况 → 该做什么决策"的规则。** 每条含：**场景 / 判据 / 依据 / 反例 / 可执行检查**。
> 判据**与具体项目无关**，是可迁移资产。使用时按"场景"检索。
> **15 类**：A 定位 · B 边界 · C 抽象 · D 数据流 · E 质量 · F 工具 · G 并发竞争 · H 失败降级 · I 状态机 · J 安全契约 · K 可观测性 · L 数据生命周期 · M 性能成本 · N 许可与防篡改 · O 数据模型与 ID 规范。

## A 类 · 定位（东西放哪）

### A1 · 一个东西该放哪一层？
- **场景**：新增模块/函数，不确定归属。
- **判据（依次问，命中即停）**：认识外部世界（`window`/`fs`/网络/`localStorage`）？→ `adapters`；受易变因素影响？→ volatile 层；是发版冻结的契约？→ `stable`；纯逻辑（无副作用）？→ `core/rules`；编排（串端口、不碰 React/window）？→ `core/usecases`；只是状态容器？→ `state`；是视图？→ `ui`。
- **依据**：依赖方向单向 + 复杂度在边界。
- **反例**：把"算哈希"写进 slice（业务进了状态层）；把 `fetch` 写进 `ui`。
- **检查**：`core/**` 无 `window`/`Date.now`；slice 内无计算逻辑。

### A2 · 状态该放哪？
- **场景**：有一个会变的值，不确定放 store / Context / 局部 / 派生。
- **判据**：跨多个顶层子树 → 全局 slice；只在某子树内 → 子树 slice；单个/相邻组件 → `useState`；**能算出来 → 不入 state，渲染时算**。
- **依据**：React「状态就近」+「避免冗余 state」。
- **反例**：`_persisting` 存进 store（应派生）；把"面板开合"放进全局 store。
- **检查**：store 里无"能由已有 state 算出"的字段。

### A3 · 常量 / 文案 / token / 键 该放哪？
- **场景**：要写一个文案 / 阈值 / 颜色 / 存储键。
- **判据**：UI 文案（含失败 label、错误横幅映射）→ `constants/text.ts`；业务常量 → `constants/`；设计 token → `styles/tokens.css`；存储键 → `stable/contracts/keys.ts`（字面量联合）。**别处一律不得重复定义。**
- **依据**：SSOT（数据只能有一个真源）。
- **反例**：组件里写 `#3b82f6`；各处写 `'doubao-projects'` 字面量。
- **检查**：lint 禁 `ui/**` 与 `*.module.css` 出现字面量色值；键名拼错编译期报错。

### A4 · 错误该在哪一层产生？
- **场景**：要写错误处理。
- **判据**：**生产者**（`adapters` / `core/rules`）**产生**错误（`{ok:false, reason, message}`，`message` 为原始原文）；**消费者**（`usecases`/`state`/`ui`）**只能转发**。
- **四条禁止**：① 禁止吞错（`catch {}`）；② 禁止改写 `message`（友好文案属展示层，按 `reason` 映射，不覆盖原文）；③ 禁止编造 `reason`（未知归 `unknown` 但保留原文，并去规则层补分类）；④ 禁止消费者兜底造错。
- **依据**：错误被掩盖 = 找不到根因；缺错误去生产者补。
- **反例**：`catch (e) { return { ok:false, reason:'unknown', message:'操作失败，请重试' } }`。
- **检查**：grep `catch\s*\([^)]*\)\s*\{\s*\}` ⇒ 0 命中；用例层无 `message:` 字面量。

## B 类 · 边界（开不开 / 改不改）

### B1 · 要不要开一个新端口？
- **场景**：想为某能力建端口。
- **判据**：**同时**满足才开 —— ① 它是**驱动外部世界**的边界；② 变更频率高或需强隔离。否则直接依赖 `core`。
- **依据**：Hexagonal 的收益是局部的，代价是全局的。
- **反例**：给每个纯函数都套端口（过度设计）。
- **检查**：端口总数受控（本项目 ≤ 4）。

### B2 · 要不要改"本不该改"的那一层（含冻结层 / 后端）？
- **场景**：想动 `electron/**` 或冻结契约。
- **判据**：改一行能省对方几十上百行 → **改**；该层能力缺失导致上层无法实现 → **改**；契约有缺陷但调用频次低 → **不动**；站点改版 → **改易变层**（与冻结层无关）。
- **改冻结层的 3 条硬约束**：① 不改已有签名（只新增/重载）；② 不改数据格式；③ **改动回写文档**。
- **依据**：目的是更好实现，不是自我设限；避免把技术债从一层搬到另一层。
- **反例**：为绕过后端缺陷，在前端堆 workaround。
- **检查**：每次改冻结层都有 B2 判据记录 + 文档同步。

### B3 · 要不要改数据格式？
- **场景**：某项存储/协议格式想改。
- **判据**：**默认不能改**。唯一例外：格式本身是**设计缺陷**（如 base64 内联致配额超限）→ 可改，但必须：① 提供**向后兼容读**；② 写入用新格式 + 记版本号；③ 作为**一条迁移**进冻结层。
- **依据**：老用户数据在磁盘上，改格式 = 数据丢失风险。
- **检查**：新格式有兼容读路径 + 版本号 + 迁移用例。

### B4 · 约束该打多大范围？
- **场景**：想引入一条全局规则（如"包必须扁平"）。
- **判据**：问"**风险在哪**" —— 只在**真正有风险处**打约束；收益局部、代价全局的规则**不全局套用**。
- **依据**：判断依据不是"哪个规则更好"，而是"风险在哪、约束就打在哪"。
- **反例**：把"入口点边界"全局套用 → `adapters → core/ports`、`ui → core/model` 全部非法，依赖链断裂。
- **检查**：每条强约束都能指出它防的具体风险。

### B5 · 要不要引入新依赖 / 库？
- **场景**：想加一个库（状态机 / 请求库 / UI 框架）。
- **判据**：先问"现有手段够不够" —— 够则不加。状态机用判别联合 + 纯函数；数据源非 HTTP 就不引请求库；无 SSR 就不引相关库。
- **依据**：拒绝过度设计；认知负担优先。
- **反例**：为 3 个状态引状态机库。

### B6 · 要不要借鉴 / 引入外部实现？
- **场景**：发现外部（GitHub / 最佳实践）有更好的实现。
- **判据**：**先过 §5.2「更好」判据 + 许可检查** —— 契合约束？更简单？有证据？成本收益？**license 兼容**（copyleft / 商用受限只学思路，不搬代码）。
- **依据**：为结果操碎心，但"更好"由**约束**裁决，不由流行度裁决。
- **反例**：因 star 高就照搬；把 AGPL 代码搬进闭源项目。
- **检查**：采纳有对照记录；无 license 冲突的代码搬运。

## C 类 · 抽象（抽不抽 / 拆不拆）

### C1 · 要不要抽共享实现？（三振出局）
- **场景**：发现相似的代码。
- **判据**：同一段代码出现 **>2 次**（第 3 次出现）⇒ **必须抽**。按性质归位：UI 交互模式 → 共享组件；纯逻辑 → `core/rules`；工具 → `lib`；常量 → `constants`；宿主调用 → `adapters`。
- **依据**：不定量要么过度抽象（第 2 次就抽，抽错方向），要么放任重复。
- **反例**：第 2 次就抽象（抽象错方向）；十几处重复弹窗逻辑。
- **检查**：`'Escape'`/`aria-modal`/`role="dialog"` 只出现在共享组件目录。

### C2 · 要不要拆 slice / 文件？
- **场景**：某个 slice 或文件变大。
- **判据**：单 slice > 300 行 / > 25 字段 ⇒ 再按**共享范围**细分；文件 > 400 行（**建议**）⇒ 拆。
- **依据**：防止退化成巨型 store / 巨型文件。
- **检查**：**人工**（eslint `max-lines` 已于 2026-10-11 **关闭**）。

### C3 · 要不要拆一个巨型组件？
- **场景**：一个组件同时含多种关注点（如 3,304 行后台视图）。
- **判据**：**按关注点拆** —— 宿主操作 → `adapters`；调度逻辑 → `core/usecases`；视图 → `ui`。纯函数（如指纹比较）→ `core/rules`。
- **依据**：一个组件不该同时含宿主操作、调度逻辑、UI。
- **检查**：无 >1000 行的组件；每类逻辑有明确归属。

## D 类 · 数据流

### D1 · 谁写状态？
- **场景**：某处要改 store。
- **判据**：**只有 `state/**` 能写**。`core/usecases`、`adapters` 绝不能写（反向依赖 = 环）；`ui` 只能调 `state` 暴露的 action，不得直接 `setState` 直改。
- **契约**：用例**返回结果**（`UsecaseResult<T>`），由 state 层写入。
- **依据**：谁拥有状态谁写。
- **检查**：`ui/**` 无 `useStore.setState()`；用例内无 store 引用。

### D2 · 事件推送怎么处理？
- **场景**：主进程/宿主推送事件。
- **判据**：适配器暴露 `subscribeXxx(cb): () => void`（**只有订阅，只转发**）；`state` 层订阅并写入（**唯一写入点**）。
- **依据**：适配器不解释、不存储。
- **检查**：适配器事件方法返回取消订阅函数，无 store 引用。

### D3 · 端口里放什么？
- **场景**：写 `core/ports/*`。
- **判据**：**只有类型**（`interface`/`type`），**零实现**；实现唯一在 `adapters`。
- **检查**：`core/ports/**` 无函数体 / 无 import 实现。

### D4 · 依赖注入落在哪？
- **场景**：要决定"用哪个实现"。
- **判据**：**装配层**（`bootstrap/container.ts`）唯一知道实现；端口注入到**用例**与**状态**；**纯规则不接收任何注入**（它本就是纯函数）。
- **检查**：`core/rules/**` 无注入参数；`bootstrap` 是唯一 import adapters 的地方。

## E 类 · 质量

### E1 · 什么该测？
- **场景**：要写测试。
- **判据**：内核规则 ✅必测；用例 ✅必测（注入 mock 适配器）；冻结层迁移 ✅必测；状态层 ⚠️只测纯 reducer；适配器 ❌不测实现细节；**UI ❌不写组件测试**（会产生**假守卫**）。
- **依据**：组件测试通过 ≠ 功能正确，且维护成本高、价值低，掩盖真正缺陷。UI 用端到端冒烟验真实用户路径。
- **检查**：测试文件只在 `core/**/tests/`、`stable/**/tests/`；`ui/**` 无 `*.test.tsx`。

### E2 · 什么时候用 Effect？
- **场景**：想用 `useEffect`。
- **判据**：**能算的不用 Effect**；交互逻辑放**事件处理**不放 Effect；Effect 必须有清理；事件与 Effect 用 `useEffectEvent` 分离；不需要重渲染的值用 ref。
- **依据**：Vercel + 官方（`rerender-derived-state-no-effect` / `rerender-move-effect-to-event`）。
- **检查**：`eslint-plugin-react-hooks` 的 `set-state-in-effect` 等 17 条 lint 通过。

### E3 · 可访问性（a11y）底线？
- **场景**：写交互组件（弹窗 / 菜单 / 表单 / 图标按钮）。
- **判据**：**交互必须键盘可达 + 焦点受控 + 有 aria 语义** —— 弹窗/菜单支持 ESC 与键盘导航；焦点管理（打开聚焦、关闭归还）；用 `role="dialog"`/`aria-modal` 等语义；图标按钮有可读标签。
- **依据**：外部对照发现的缺口（见 `references/09-求最优与补缺.md`）。
- **检查**：`'Escape'`/`aria-modal`/`role="dialog"` 只在 `ui/common/`；共享组件有键盘处理。

## F 类 · 工具

### F1 · 依赖边界用什么工具？
- **场景**：要强制分层。
- **判据**：选**能证明规则会咬**的工具。需要"查环 + 层间方向 + 可验证失败" → `dependency-cruiser`（eslint `no-restricted-imports` 做不到）。
- **落地**：多条规则全 `error` + 折进 `npm run check` + **故意违规必须失败**。
- **检查**：`lint:boundaries` 在故意深导入时失败。

### F2 · 样式用什么方案？
- **场景**：要定样式方案。
- **判据**：**标准 + 唯一真源** → 原生 CSS + CSS Modules + `tokens.css` 为 SSOT。**不用 Tailwind**（token 打散进 className，破坏 SSOT）、**不用 CSS-in-JS**（运行时开销）。第三方库**只用其官方 CSS 变量**主题化，不写类名覆写。
- **检查**：组件只引 `var(--*)`；字面量只在 `tokens.css`。

## G 类 · 并发与竞争

### G1 · 共享资源要不要加锁/占用？
- **场景**：多任务可能同时用同一资源（账号、抓取通道）。
- **判据**：**有竞争就必须有保护** —— 内存态占用集合（忙集合）+ 负载计数；被占用者跳过或排队；全忙返回 `all-busy` 并排队；占用带超时自动释放。
- **依据**：竞争点无保护 = 脏数据 / 重复发送。
- **检查**：抓取有互斥锁（"上一次抓取还没结束"）；账号忙超时（1h）。

### G2 · 要不要幂等键？
- **场景**：重复触发可能造成重复副作用（重复点菜单、重复落盘）。
- **判据**：**可能被重复触发的写操作必须幂等** —— 发送用 `sessionId` 去重；图片外置同 `dataUrl` 返回同一 `img://`。
- **检查**：同图连续两次外置返回同一引用；同 `sessionId` 不重复发送。

### G3 · 并发度怎么定？
- **场景**：要跑一批任务。
- **判据**：**按资源瓶颈定，不拍脑袋** —— 账号并发 = 1；API 并发按 provider 限（默认 3）；扫描并发 3；用**并发池**而非 `Promise.all` 全开。
- **检查**：并发数是具名常量（SSOT），非散落魔法数。

### G4 · 什么时候合并 / 防抖？
- **场景**：高频操作（拖拽、输入、连续编辑）。
- **判据**：**同 key 的连续操作在窗口内合并** —— 撤销合并 800ms；持久化防抖 600ms；窗口值走 `ClockPort` 以便可测。
- **检查**：连续 10 次移动合并为 1 步；600ms 内只写 1 次。

### G5 · 重启后未完成任务怎么办？
- **场景**：应用重启，存在未完成的生成/任务。
- **判据**：**明确"续传 or 放弃"并写进契约** —— 本项目**重启即放弃**（打开工程时清理未完成 apiJob 与在途标记）；无真正断点续传时不假装有。
- **检查**：`openProject` 清理在途任务。

## H 类 · 失败处理与降级

### H1 · 失败怎么分类？
- **场景**：要处理失败。
- **判据**：**正则驱动 + 顺序遍历 + 命中即停 + 兜底 unknown**；分类表是唯一真源；未命中归 `unknown` 但保留原文。
- **检查**：表驱动单测（每条失败文案 → `{kind, retryable, switchAccount}`）。

### H2 · 失败后做什么决策？
- **场景**：分类后要决定动作。
- **判据**：**决策函数输出三选一** —— `give-up`（不可重试或超次数）/ `retry-switch`（换号）/ `retry`（原地重试）；`maxRetry` 是具名常量。
- **依据**：分类（是什么）与决策（做什么）分离，各可单测。
- **检查**：决策函数有单测；`maxRetry` 非硬编码。

### H3 · 什么时候"停手"而不是重试？
- **场景**：可能触发风控/封号。
- **判据**：**安全优先** —— 命中"安全确认 / 人机验证 / 风控拒绝"→ **停止自动重试**（防封号），交人工。
- **依据**：重试可能加重风控，代价远大于收益。
- **检查**：`safety-promise`/`human-verification`/`risk-refuse` → `retryable:false`。

### H4 · 要不要降级链？
- **场景**：主通道可能不可用。
- **判据**：**有可用替代通道就建降级链，且在边界内部实现** —— 抓取：多帧 → 单页（**死通道要移除，不留死代码**）；选择器：多级降级。
- **检查**：降级链在 adapter 内部；`via` 字段可观测。

### H5 · 重试退避怎么定？
- **场景**：重试间隔。
- **判据**：**阶梯退避 + 上限** —— API 退避 `[2s, 8s, 30s]`；连续 N 次（5）网络失败判失败；退避值走 `ClockPort`。
- **检查**：退避序列是具名常量。

## I 类 · 状态机建模

### I1 · 要不要引入状态机库？
- **场景**：有复杂状态流转。
- **判据**：**判别联合 + 纯函数够用就不引库**。
- **依据**：拒绝过度设计。
- **检查**：无状态机库依赖；状态转移有纯函数单测。

### I2 · 状态怎么表达？
- **场景**：要建模状态。
- **判据**：**判别联合**（`type` 作判别式）+ 显式终态集合 —— 账号：新增/已登录/失效/额度不足/忙；API 任务：`queued→submitting→running→downloading→done|failed|cancelled`；抓取：`scanning→found→working→done`。
- **检查**：终态穷举；非法转移可拦截。

### I3 · 乐观更新怎么做？
- **场景**：异步结果未返回前想先反馈。
- **判据**：**先占位后落值** —— 用 `useOptimistic` 或占位标记；在途标记；结果到达再写真实值，可回滚。
- **检查**：占位状态可回滚。

## J 类 · 安全与契约

### J1 · 契约哪些能加、哪些不能改？
- **场景**：要动接口 / 协议 / provider。
- **判据**：**可加不可改** —— 新增 provider / 新增方法可以；改已有签名或格式不行（除非过 B2/B3）。
- **检查**：差集比对（宿主方法名集合 vs 调用面集合）为空。

### J2 · 密钥怎么处理？
- **场景**：要存 / 读 / 传密钥。
- **判据**：**绝不落明文** —— 用系统级加密；不可用则**拒绝保存**；对外只暴露脱敏读口（`hasKey`/`keyHint`）；日志全量脱敏。
- **检查**：无明文密钥；日志无密钥。

### J3 · 路径怎么防穿越？
- **场景**：解析用户/外部提供的路径。
- **判据**：**解析后强制留在允许根内**；名字去分隔符；不接收任意路径。
- **检查**：资源协议解析后仍在允许根内。

### J4 · 要不要"零注入"？
- **场景**：想用 JS 伪装环境（UA/指纹）。
- **判据**：**不改 `navigator`/`screen`/`webgl`** —— 引擎指纹 JS 改不了，改反而留可探测痕迹；声明版本**不得高于真实引擎**。
- **依据**：`10` 实测（改 → 被判定伪造）。
- **检查**：站点适配器无注入代码。

## K 类 · 可观测性

### K1 · 该记什么日志/埋点？
- **场景**：要加日志。
- **判据**：**关键路径可观测** —— 错误横幅（类型→文案）；操作日志（每次变更 `{at, projectId, type, detail}`）；关键阶段埋点（scan-fail / scan-done …）；诊断日志落盘（双击 `.app` 时 stderr 不可见）。
- **检查**：错误横幅 + 操作日志 + 埋点齐备。

### K2 · 崩溃怎么捕获？
- **场景**：渲染或进程崩溃。
- **判据**：**渲染层两级错误边界 + 主进程崩溃捕获** —— 全局边界（包裹 App）+ 画布边界（包裹画布）；主进程 `child-process-gone` → 写日志。
- **检查**：全局/画布边界存在；崩溃有日志。

## L 类 · 数据生命周期

### L1 · 数据怎么迁移？
- **场景**：格式变更。
- **判据**：**纯函数 + 按序执行 + 先拷后删 + 可独立回归** —— 迁移是纯函数（旧→新），启动按序跑，删除前先拷贝，每条可单测。
- **检查**：迁移有 golden sample 测试。

### L2 · 大资产怎么存？
- **场景**：图片 / 视频。
- **判据**：**绝不内联 base64** —— 图片外置 `img://`（内容哈希命名，同图同引用）；视频**必须落盘**；一律用缩略图 `?w=`。
- **依据**：base64 内联 = 存储配额超限根因。
- **检查**：无 base64 内联；视频落盘；缩略图 `?w=`。

### L3 · 什么时候清理？
- **场景**：缓存 / 会话。
- **判据**：**清理必须保住不可再生资源** —— 清浏览器缓存**保留登录态**；删账号才清会话；不碰 `Cookies`/`Local State`。
- **检查**：清理范围有白名单。

## M 类 · 性能与成本

### M1 · 什么时候优化？
- **场景**：觉得慢。
- **判据**：**先测量再优化** —— 用 `<Profiler>` / DevTools 定位，再 `memo`/`useDeferredValue`；不做无测量优化。
- **检查**：优化点有测量依据。

### M2 · 长列表 / 大图怎么办？
- **场景**：渲染大量节点 / 图片。
- **判据**：**只渲染可见 + 一律缩略图** —— `onlyRenderVisibleElements`；长列表 `content-visibility`；图片一律 `?w=`（原图 2~20MB）。
- **检查**：画布开启可见渲染；无原图直载。

### M3 · 包体积怎么办？
- **场景**：重组件 / 大依赖。
- **判据**：**动态导入 + 禁 barrel** —— 站点适配器 / 图片编辑器 / vision bundle 走 `lazy`；禁 barrel（每层小入口点）。
- **检查**：重组件 `lazy`；无巨型 `index.ts` 全导出。

## N 类 · 许可与防篡改

### N1 · 机器码怎么生成？
- **场景**：要绑定设备。
- **判据**：**用稳定硬件标识，排除会变的** —— 主键硬件序列号，辅键硬件 UUID，兜底 CPU+内存；**排除** hostname/MAC/IP（会变）；生成后锚定落盘，主键未变则沿用旧码。
- **依据**：切网 / 升级内存不应导致重新激活。
- **检查**：机器码不含 hostname/MAC/IP。

### N2 · 许可怎么验签？
- **场景**：要校验授权。
- **判据**：**非对称验签 + 防篡改 + 一次性码** —— 激活码用非对称签名（**私钥不进客户端**）；许可文件用 HMAC 防篡改；一次性码用 AEAD 加密存已用表。
- **检查**：客户端无私钥；许可文件改动 → 判 `tampered`。

### N3 · 时间怎么防回拨？
- **场景**：授权有有效期。
- **判据**：**可信时间源 + 单调时钟 + 落盘基线** —— 读可信 HTTPS `Date` 头 + `hrtime` 单调锚点 + 持久化基线（HMAC）；检测回拨 → `tampered`。
- **依据**：回拨可让过期授权复活。
- **检查**：回拨能被检测。

### N4 · 许可失败怎么处置？
- **场景**：解密 / 验签失败。
- **判据**：**fail-close** —— 纯离线客户端解密失败即**拒绝激活**，不降级放行。
- **检查**：失败路径拒绝而非放行。

## O 类 · 数据模型与 ID 规范

### O1 · 数据模型怎么表达？
- **场景**：定义实体。
- **判据**：**判别联合 + id 引用不嵌套** —— 多态实体（如 8 类节点）用 `type` 判别式；关系用 id 引用（`accountId`/`libId`），不深层嵌套。
- **检查**：节点是判别联合；无深层嵌套对象。

### O2 · ID 怎么生成？
- **场景**：新建实体。
- **判据**：**前缀 + base36 + 计数**，每类实体前缀固定（工程 `p_`、账号 `acc_`、预设 `pre_`、节点 `t/m/vid/gv/ig/a/e/grp`）；前缀是具名常量（SSOT）。
- **检查**：ID 前缀唯一真源；无裸随机 ID。

### O3 · 顺序 / 引用怎么维护？
- **场景**：节点间有引用 / 顺序。
- **判据**：**顺序显式存储 + 环检测** —— 文本引用写 `referenceOrder`；连线顺序写 `linkOrder`；成环必须拦截。
- **检查**：环检测用例 W6；`referenceOrder` 单向。

### O4 · 默认值放哪？
- **场景**：实体有默认值。
- **判据**：**数据默认值归 `model`，不归 `rules`** —— 8 类节点默认值属数据（`core/model/defaults.ts`），`core/rules` 只放逻辑。
- **检查**：`rules` 无数据默认值。

### O5 · 层级 / 组关系怎么处理？
- **场景**：有父子 / 分组。
- **判据**：**父子用 `parentId` + 删除时把子节点位置叠加回父**（剥离 `parentId`/`extent`）；打组需 ≥2 个非组节点；组 `zIndex` 固定置底。
- **检查**：删组不丢子节点位置。

# 第三部分 · 通用方法（采集约束 · 排里程碑）

## Step 0 · 认清项目形态（三问）
绿地还是"已知形态应用的重写"？（重写 → 认知负担优先，不为未知需求留抽象）／需求源可信吗？（逆向产物 → 分类不可靠，需人工复核）／复杂度在哪？（在**边界** → 端口化；在**内核** → 端口化是过度设计）

## Step 1 · 列约束（列"约束"，不是列"决策"）
逐类过：① 形态 ② 可信度 ③ 复杂度分布 ④ 变更频率分布 ⑤ 成本不对称 ⑥ 冻结约束 ⑦ 可测性 ⑧ 数据/契约。

## Step 2 · 逐条翻译（约束 → 结构）
| 约束信号 | 结构决策 |
|---|---|
| 复杂度在驱动外部世界 | 端口-适配器 |
| 变更频率不均匀 | volatile 集中 + 冻结独立 + 中间夹内核 |
| 成本不对称 | 契约边界表 + 成本判据（B2） |
| 发版即冻结 | 独立层 + 禁反向依赖 + 迁移 |
| 必须可纯测 | 依赖注入 + 纯逻辑抽函数 |
| 分类不可靠 | 不按业务域切，改按共享范围/变更频率 |

## Step 3 · 用判据裁决
拿具体决策去**第二部分判据库**逐条裁决（放哪层 → A1；开不开端口 → B1；抽不抽 → C1；改不改 → B2 …）。

## Step 4 · 落点校验
对 Step 1 的**每条约束**，检查是否有**具体落点**（某目录 / 某契约注释 / 某条 lint）。**没有落点 = 必然重踩**。

## Step 5 · 排里程碑
按依赖顺序，地基优先：契约与边界工具 → 数据层 → 核心域 → 边界实现 → 端到端。**先建"证明规则会咬"的机制，再写业务。**

# 第五部分 · 求最优架构（穷尽手段）

> **心态：为结果操碎心。** 不满足"够用"；默认自己的架构**有缺陷，直到证明过**；主动找"更好"，而不是等它出现。
> **原则：外部是"候选"，本项目约束是"裁判"（见元原则）。** 不闭门造车，也不照单全收。

## 5.1 手段清单（想各种办法）

| # | 手段 | 具体做法 |
|---|---|---|
| 1 | **外部最佳实践**（技能 / 官方文档 / 标准） | 逐条对照 → 标 `已覆盖 / 不适用 / 缺口` |

| 6 | **多模型交叉** | 用不同模型对同一决策**提反对意见**，找自己的盲点 |
| 7 | **反向验证** | 故意找反例 / 压力测试 / 假设自己是攻击者与新手 |

## 5.2 判据：什么叫"更好"？（不能只看"新 / 流行"）
- **更契合本项目约束？**（约束是裁判）
- **更简单？**（认知负担更低）
- **有证据 / 被验证过？**（真实项目用过、有数据）
- **引入成本 vs 收益？**（判据 B5 引不引依赖、B2 改不改）
- **许可兼容？**（学习前必查 license，见 5.3 红线）

## 5.3 GitHub 同类项目：搜索 → 评估 → 学习
- **搜索**：按"技术栈 + 形态 + 领域"组合关键词（如 `react flow` + `infinite canvas` + `AI image generation`；`electron` + `node editor`）。
- **评估维度**：架构相似度 / 代码质量 / 活跃度（近期提交）/ star / **license** / 是否解决同类难题（站点对抗、账号池、去重）。
- **学习方式**：`clone` 到**工作区之外**阅读（不改本仓）；**提取"模式"而非照搬代码**；把可迁移做法抽象成判据 / 模板。
- **⚠️ 许可红线**：学习 ≠ 照抄。**copyleft（GPL / AGPL）** 与**商用受限**许可**不得**直接把代码搬进本项目；只学思路。

| 触发 | 动作 |
|---|---|

| 站点改版 / 后端变更 | 更新对应 reference（volatile 层） |
| 某条判据被证伪 | 修正或废弃，写明原因 |

**进化流程**：
1. **记**：在 `references/10-进化日志.md` 追加一条（日期 / 类型 / 变更 / 依据 / 影响）。
2. **改**：更新 SKILL.md（判据库 / 推理链）或对应 reference；**保持单一真源**（别在两处写）。
3. **验**：规则类变更 → 更新检查清单 / 验收用例。

**自进化的约束（不能破坏架构）**：
- 新知识必须**可追溯到约束或证据**，不得凭感觉加规则。

- 默认模板的偏离必须**写明原因**。
- 日志只追加、不删改（保留演进轨迹）。
