## 一、取证：两个方法在后端的**真身**（不是"搜不到就当没有"）

| 方法 | 前端实现 | 后端 handler | **收什么** |
| --- | --- | --- | --- |
| `FilePort.revealPath(p)` | `guard(a => a.revealPath(p))` | `reveal-path`（`main.js:1904`）＝ **`shell.showItemInFolder(p)`** | **真实路径**（不解析 `img://`） |
| `MediaPort.showInFolder(ref)` | `guard(a => a.showInFolder(ref))` | `show-in-folder`（`main.js:1273`）＝ **先 `resolveImageRef(ref)`** 再 `showItemInFolder` | **`img://` 引用** |
| `MediaPort.resolveImageRef(ref)` | `guard(a => a.resolveImageRef(ref))` | `img-resolve`（`main.js:1161`） | `img://` → 路径 |

**源侧的消费者**（`expanded_components/**` 全检索）：

- `_Component42.jsx:1132-1134`（**节点右键菜单项 3**）：
  ```js
  if (!!ue && !!/^img:\/\//i.test(ue) && !!window.api && typeof window.api.showInFolder == 'function') {
      await window.api.showInFolder(ue);        // ← 传的是 img:// 引用
  ```
- `resolveImageRef` / `img-resolve`：**源前端一处都没有**（`main.js:739` 的解析只被主进程内部 8 处调用）。

⇒ 两条结论（都不是"猜"）：
1. **`showInFolder` 与 `revealPath` 不是重复** —— 一个收 `ref`、一个收 `path`；**源用的是前者**；
2. **`resolveImageRef` 前端不需要** —— 解析是主进程内部的事。

## 二、🔴 顺带查出一个**真 bug**（并修掉）

`ui/canvas/NodeContextMenu.tsx` 的「打开文件所在位置」：

```ts
const canReveal = typeof dataUrl === 'string' && /^img:\/\//i.test(dataUrl);   // ← 只可能是 img://
...
const r = await hostOps.revealPath(dataUrl);     // ← 却传给了"只认真实路径"的那个
```

⇒ `img://xxx` 进到 `reveal-path` ⇒ `shell.showItemInFolder('img://xxx')` ⇒ **该功能实际打不开**。
而该文件的头注当时写着「✅ `hostOps.revealPath`（已接）」——**假声索**（"已接"≠"接对了"）。

这也正是 `MediaPort.showInFolder` **零消费的根因**：**该用它的地方用错了方法**。
