**`ipcGuard` 本体**（`main.js:3095`）：
```js
const ipcGuard = (fn) => async (...args) => {
  try { return await fn(...args); }
  catch (err) { return { ok: false, error: (err && err.message) || String(err) }; }  // ★ 原样透传
};
```

### ★ 因此正解**不是**"无脑包 62 个"

债的解法本就写了「**或明确豁免并留痕**」⇒ 按实况分两类：

| 类 | 数量 | 处置 |
|---|---|---|
| 函数体**无** `try/catch` | **15** | **接线**（包 `ipcGuard`）—— 它们才是异常会逃的 |
| 函数体**自带** `try/catch` | **47** | **明确豁免**（与守卫等价 ⇒ 不重复包，判据 C1：同一模式不叠两层） |

## 四、探针（先红后绿 · **守卫式**）

   先红：退出码 1（期望 1）· expect-out 命中（RED：有 handler 两者皆无）
   ✅ 还原校验通过（sha256 一致）· 后绿：退出码 0（GREEN）· ✅ 探针成立

## 五、反向探针（零炸）

| 口径 | 命令 | 结果 |
|---|---|---|

| 守卫复跑 | `node /tmp/scan-ipcguard.cjs` | ✅ 67 = 20 + 47 + **0** |

**零炸三问**：

1. **哪些行为被改了？** —— **只有"handler 抛异常"这一条路径**：从 **rejected IPC** 变为 **`{ok:false, error:<原文>}`**。
   ⚠️ 渲染侧**两端都能拿到原文**（适配器的 `guard()` 本就把 rejection 转成 `err(..., toMessage(e))`）⇒ **用户可见行为不变**，变的是**通道形状**（统一成判别联合）。
2. **改前能走的路径仍能走吗？** —— 正常返回路径**一字未动**（`ipcGuard` 只包了 try/catch，`return await fn(...)` 原样透传）；1387 tests 绿。
3. **改前会失败的仍失败吗？** —— 是；且**原文保留**（`err.message`）✓。

**用户可感知变化（显式声明）**：**无**（成功路径零变化；失败路径的**文案同源**，只是从"IPC 拒绝"变成"结构化错误"）。
