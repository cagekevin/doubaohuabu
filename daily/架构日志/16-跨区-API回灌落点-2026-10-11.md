## 五、决策留痕

1. **落点放哪：`apiLanding.ts` 作为 `canvas` 片的片段**（不是新 slice，也不是 `subscriptions.ts` 内联）。
   理由：① `canvas.ts` 代码行已 **383/400**（`max-lines`），加三个 action 必红；② 它写的正是 `nodes`/`library`
   ⇒ **归属仍是 `canvas` 片**，与 `materialBatch.ts` **同法**；③ 放 `subscriptions.ts` 会让「订阅」文件混进业务。
2. **`attachVideoResultToNode` 只收 `{url, attempt}`**：源还传 `name`/`accountName`，但它们在 genvideo 分支**被忽略**
   （只在「网格新建」分支被读）⇒ 不收，避免「收了不用的字段」。
3. **toast 的 `success` 档**：**补进 SSOT**（而不是把 `success` 映射成 `info`）。理由：源 `.app-toast-success` 确有独立样式，
   且 `--color-success` 已在 token 里 ⇒ 保真成本 ≈ 0；映射会**永久丢一档语气**。
4. **`applyApiJobEvent` 决策的 `feed` 字段不消费**：见 §四（TD-16-84）。**没有**为它造一个「落了没人读」的 action。
5. **不做**：`imageGenKeyParams` 的**生产者**（`bindImageGenKey`）—— 那是「API 图生图 key 绑定」另一条链，
   同批落会变成「两件事一起做」（零炸：只做被要求的那件）。

## 九、教训 / 复用点

1. **「有实现、无消费」的用例，最后一跳往往不止一个 action** —— 本条线索（`docs/14` §4）只点了 **3 个** action，
   实际还需要 **第 4 个**（`addToLibrary`：源 27101，与 `setLibrary` **不是一回事**，后者是整体替换）。
   ⇒ **债务是线索，不是清单**：动手前要按**决策对象的字段**逐个点一遍。
2. **契约的「少一档」会一路顶到消费者**：`ToastLevel` 漏 `success` ⇒ API 回灌的成功提示**根本传不进来**。
   这类「枚举比现实少」的缺口，**只有在真接线时才会暴露**（`analyze.ts` 里那份手写三档也是同源）。
3. **`max-lines` 会逼出正确的结构**：`canvas.ts` 到顶 ⇒ 自然走向「片段 + 组合」，
   比「为省事放宽闸」正确得多。
