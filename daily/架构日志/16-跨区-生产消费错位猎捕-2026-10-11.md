## 八、施工（TD-03-18 · 2026-10-11 · 架构师改码7步法）

**落点 = 根因层**：`core/usecases/sendQueue.ts` 的 `TransportFn` 契约（**不是**症状层 `state/batchSend` 的那张 Map）。

### 断链诊断（差一步）

`prepare` 的产物 `PreparedSend` 是 `{account, operation, recipe}` —— **它算了 `site` 却只返回 `account`**；
`transport` 又只收 `operation` ⇒ `sendOneNode` 拿到 `{account, operation}` 后**在调用点把账号丢了**。
下游 `state/batchSend.transport` 要发消息（需 account ＋ site），只能造 `Map<报文对象, SendAccountChoice>`
（`picked`）靠**引用相等**反查 —— 其注释自认"用 nodeId 反查会取到第一个节点的账号"（多节点批量下必错）。

## 九、补刀（2026-10-11）—— **`forceAccountId` 是幽灵参数，已删**

> §八 当时写「`forceAccountId` 经重判**保留**（队列已占号的合法告知，非旁路）」——**那个重判是错的**。
> 用户裁定「都算[偷懒]」后重新取证，真相更严重。

### 取证（一步就到根）

**`state/batchSend.ts` 的 `prepare` 签名是 `(nodeId) => {…}` —— 它压根没有 `opts` 形参**，
自然也**从不读 `opts.forceAccountId`**。⇒ 那个字段：

| 环节 | 事实 |
| --- | --- |
| 声明 | `PrepareSendOptions.forceAccountId`（`core/usecases/sendQueue.ts`）＋ `SendOneInput.forceAccountId` |
| 传入 | `state/sendQueue.ts` 的 `runItem` 传 `d.accountId` |
| **读取** | **无** —— 唯一实现忽略 `opts` ⇒ **幽灵参数**（母体 M6） |
| 后果 | 队列 `reserve` 占住 A（A 进忙表）⇒ `prepare` **自己又选一次号**，因 A 忙而**跳过 A 选到 B**（或 `all-busy` 失败）⇒ **面板显示的账号 ≠ 实际发送的账号**，且占的号白占 |

⇒ 这比"选号两次"更重：**它不是冗余，是错的**。

### 改动（4 文件 · 只留一套选号）

| 文件 | 改动 |
| --- | --- |
| `core/usecases/sendQueue.ts` | **删 `forceAccountId`**；新增 `ForcedSendChoice {account, site, degraded?}`；`PrepareSendOptions.forced` / `SendOneInput.forced`；`sendOneNode` 透传；失败返回的 `accountId` 改取 `forced?.account.id` |
| `state/batchSend.ts` | `prepare` **签名收下 `opts`**（原先忽略它正是幽灵的成因）；`opts.forced` 有 ⇒ **直接用**（构造 `SendAccountChoice`，不再查池）；无 ⇒ 走原池选号（`runBatchSend` 传 `{}` 的正常路径） |
| `state/sendQueue.ts` | 新增 `forcedChoiceOf(accountId)`：把已占账号 ＋ `ports.sites[type]` 组装成已定选择；`runItem` 传 `forced:` 而非裸 id |
